1. 프로젝트 개요

1-1. 배경: 해외 고객 C/S 업무

산업용 전력·자동화 제품(변압기, 차단기, 인버터, PLC, HMI 등 23종)을 쓰는 해외 고객이 문의를 보낸다. 고객은 15개 언어를 쓰고, 문의는 5개 경로(이메일, 파트너 포털, 웹 양식, 전화, 채팅)로 들어온다. 전체의 44%가 영어가 아닌 언어다.

문의는 10개 유형으로 나뉜다.

구분유형건수
문서·표로 답이 끝나는 문의기술 사양 600, 매뉴얼 400, 펌웨어 350, 인증·규격 3501,700
판단이나 확정이 필요한 문의견적 300, 납기 350, 보증 300, 설치 4501,400
사고 처리고장 550, 반품 350900

상담원은 한 건마다 다음 일을 한다.

  1. 본문을 읽고 유형과 긴급도를 판단한다.
  2. 규칙표 네 종류(우선순위 7줄, 담당 부서 111줄, 필수 정보 110줄, 처리 기한 120줄)를 찾는다.
  3. 영어 문서 107개에서 근거를 찾는다.
  4. 고객 언어로 답을 쓴다.

처리 기한(SLA)은 두 가지다. 첫 응답 기한은 접수부터 첫 답까지이고, 해결 기한은 접수부터 해결까지다. 해결 기한은 고객 회신을 기다리는 동안 멈춘다. 기한은 고객 등급(PLATINUM / GOLD / STANDARD)과 우선순위(P1~P4)에 따라 달라진다.

이 프로젝트의 데이터는 운영진이 제공한 합성 데이터다. 수치는 실제 값이 아니라 경향으로 읽는다.

1-2. 프로젝트 목적

문의가 들어오는 순간 에이전트가 분류, 우선순위, 담당 부서, 처리 기한, 추가 정보 요청, 문서 기반 답변 초안을 먼저 만든다.

  • 위험이 낮은 단순 정보 문의는 에이전트가 자체 검증을 통과한 답변을 바로 발송한다.
  • 그 밖의 문의는 상담원이 확인·수정·승인한 뒤 발송한다.
  • 반품 승인·거절, 견적 금액, 납기 확정은 사람이 한다.
  • 답변에는 문서 근거와 표에서 조회한 값만 쓰고, 어디서 가져왔는지 남긴다.

3-1. 주요 목표

3-2. 기대효과

대상효과
상담원읽기·분류·규칙 찾기·문서 검색·초안 작성이 줄고 확인·수정·승인이 남는다. 초안 옆에 한국어(또는 영어) 번역을 함께 보여 주므로 15개 언어를 몰라도 처리할 수 있다
고객저위험 정보 문의는 접수 직후 답을 받는다(지금은 중앙값 15.2시간). 그 밖의 문의도 고객 언어로 빠른 첫 응답과 진행 안내를 받는다. 요청이 여럿이어도 모두 답을 받는다

전문 부서이관 후보로 표시된 문의를 요약·근거·빠진 정보가 정리된 상태로 확인한다

효과의 크기는 합성 데이터 기준 추정이다. 실제 단축 시간은 시연과 채점 결과로 제시한다.

5-2. 자동 발송 기준

자동 발송은 요청 단위로 판정한다. 언어 모델을 쓰지 않고 규칙으로만 판정한다.

대상

항목기준
글의 종류정보 요청 문안과 답변. 진행 안내는 대상이 아니다 (상담원 승인)
문의 유형기술 사양, 매뉴얼, 인증·규격. 한 메일에 여러 요청의 답이 묶이면 모두 이 세 유형이어야 한다

합격 조건 (모두 통과해야 발송)

#조건
1초안의 인용이 근거 안에 있고, 숫자가 조회한 표 값과 같다
2답변이면 처리에 꼭 필요한 정보가 빠지지 않았다
3확인 표시(확신 낮음, 판정 실패, 근거 없음, 반품 사유 확인 필요 등)가 하나도 없다
4긴급도가 안전·설비 정지가 아니다

하나라도 어긋나면 발송하지 않고 "자동 발송 보류: {이유}"를 표시해 상담원 승인으로 넘긴다.

과거 4,000건 중 대상 유형은 1,350건(34%)이다. 이 가운데 72건은 실제로 이관된 건인데(인증서 미보유 등), 이런 건은 근거가 없어 조건 3에서 걸러진다.

사람이 반드시 승인하는 것

  • 펌웨어, 고장, 반품, 보증, 설치, 견적, 납기 문의의 글
  • 진행 안내
  • 반품 승인·거절, 견적 금액, 납기 확정이 담긴 모든 글

자동 발송한 글은 메시지 이력에 보낸 쪽을 "시스템"으로 남기고, 접수함과 문의 상세에 "자동 발송됨"을 표시한다. 자동 발송한 답변도 첫 응답으로 인정한다.

5-3. 복합 문의 처리

나눈 요청(명세서의 "하위 문의")은 각각 하나의 문의처럼 다룬다.

항목방식
나누기한 문의의 요청을 나눈다. 상한은 3개로 두고, 넘을 때의 표시 기준은 다음 회의에서 정한다
처리요청마다 따로, 동시에 처리한다 (긴급도 → 정보 추출 → 규칙 → 근거 → 초안)
상태·기한·담당요청마다 따로 가진다. 접수함에는 요청마다 한 줄씩, 각자의 담당 부서 접수함에 보인다
대표 상태문의 전체를 보여 줄 때는 끝나지 않은 요청 중 가장 급한 요청의 상태를 쓴다. 모두 끝나면 해결
발송준비된 요청부터 발송한다. 다른 요청을 기다리지 않는다. 동시에 준비되고 담당 부서가 같으면 한 메일에 묶을 수 있다
상태 목록메일 끝에 전체 요청의 현재 상태를 고객 언어로 적는다 (예: 1번 문의: 이 메일로 답변, 2번 문의: 추가 정보 확인 중). 예상 완료 시각은 쓰지 않는다
승인요청별로 5-2 기준을 적용한다. 예: 매뉴얼 답변은 자동 발송, 펌웨어 답변은 상담원 승인
해결답변을 보낸 요청만 해결로 바뀐다
저장발송 결과는 메시지 이력에 요청 순번과 함께 남긴다. 저장 구조는 DB 설계에서 확정한다

5-4. 견적·납기·반품 문의

문의에이전트가 하는 일사람이 하는 일
견적제품·수량·정가·합계·표준 납기를 안내하는 초안을 만든다. 초안에 "정확한 견적(수량 할인 등)은 영업 담당이 별도로 안내한다"는 문장을 넣는다. 이관하지 않는다초안 승인, 할인·수량 조건을 반영한 확정 견적 안내
납기표준 납기를 안내한다. 확정 출하일은 쓰지 않는다초안 승인, 납기 확정
반품사유(제품 결함 / 고객 사정)를 규칙으로 구분해 담당 부서를 정하고, 정책 조항과 예상 처리 절차를 제시한다. 구분이 애매하면 "확인 필요"를 표시한다승인·거절 결정

과거 견적 답변 246건 중 161건은 단가가 정가와 달랐다. 할인 규칙이 표에 없으므로 에이전트는 금액을 확정하지 않는다.

반품 사유 구분은 규칙으로 먼저 만들고 검증용 데이터에서 일치율을 잰다. 낮으면 언어 모델 판별을 도입한다.

7-2. 역할 분담: 읽기는 언어 모델, 결정은 규칙, 확정은 사람

근거가 없으면 초안을 만들지 않고 상담원에게 넘긴다.

기술언어 모델의 비용·지연, 같은 입력에 답이 조금씩 다름규칙 단계는 언어 모델 없이 처리한다. 시간 제한과 1회 재시도를 둔다. 시연 문의는 미리 확인한다

일정MVP 범위가 기획서 v1.1보다 넓어졌다 (고장 진단·이관 후보·대시보드·자동 발송·번역 표시)발표일이 11-10으로 확정되어 개발 기간이 늘었다. 10-30에 기능을 동결하고, 늦어지면 8-5 순서로 미룬다
일정한 기능이 여러 역할에 걸쳐 서로 기다리는 지점이 많다첫날 상태 객체·API·언어 모델 출력 모양을 합의한다. 화면은 가짜 응답으로 먼저 만든다. 이후 변경은 PR로만 한다
