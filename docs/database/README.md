# database — 데이터베이스 설계 및 SQL 관리

## 목적
해외고객향 C/S 대응 AI Agent 프로젝트의 **테이블 구조, 관계, 제약조건 및 데이터베이스 설계 근거**를 SQL 파일 중심으로 관리합니다.

## 원본 형식
- **`*.sql`** — 데이터베이스 스키마와 관련 정의를 관리하는 기본 형식입니다. `schema.dbml`을 필수 원본으로 사용하지 않습니다.
- SQL 파일에는 실제로 합의된 DDL(`CREATE TABLE`, `ALTER TABLE`, PK/FK, UNIQUE, INDEX 등)을 기록합니다.
- ERD 이미지 또는 PDF는 필요할 때 SQL 정의를 기준으로 생성하는 **참고·제출용 산출물**입니다. 도식만 수정하고 SQL을 그대로 두지 않습니다.
- 아직 SQL 스키마 파일이 업로드되지 않았으므로 파일명, 테이블, 관계 및 폴더를 임의 생성하거나 확정하지 않습니다.

## SQL 파일 작성 규칙
1. 프로젝트에서 사용하는 **DBMS 및 버전**을 먼저 확인하고 해당 방언에 맞는 SQL을 작성합니다.
2. 테이블·컬럼은 팀에서 합의한 용어와 명명 규칙을 사용합니다. 데이터 타입, NULL 허용 여부, 기본값, PK/FK, UNIQUE, CHECK 등 제약조건을 명확히 정의합니다.
3. 테이블 간 참조 관계와 인덱스는 실제 요구사항에 근거해 작성합니다. 확정 전 임의 테이블을 생성하지 않습니다.
4. 초기 생성용 스키마 SQL과 운영 중 변경을 적용하는 마이그레이션 SQL은 **역할을 구분**합니다. 마이그레이션을 도입한다면 이미 적용된 변경 파일은 덮어쓰기보다 새 변경 파일로 이력을 남깁니다.
5. SQL 스크립트의 **실행 순서, 의존 관계, 대상 DB, 초기화 방법**이 정해지면 README에 명시합니다. 검증되지 않은 실행 명령은 기재하지 않습니다.
6. 샘플 데이터는 필요할 때 별도 합의 후 관리합니다. 실고객 개인정보, 비밀번호, 인증 정보, 비밀키는 SQL에 포함하지 않습니다.

## 원본·ERD·실행 스키마의 관계
- Git에서 관리하는 SQL은 **검토 가능한 설계 및 변경의 원본**입니다.
- 애플리케이션 ORM 모델이나 별도의 마이그레이션 도구를 사용하는 경우, 어떤 항목이 **실제 DB 스키마 변경의 기준**인지 팀에서 합의합니다. SQL·ORM·마이그레이션·실제 DB 사이에 차이가 없는지 확인합니다.
- ERD는 SQL과 일치하는지 검증합니다. 설계 이미지는 SQL을 대체하지 않습니다.

## 변경 및 버전 관리
1. 버전별 복제 디렉터리(`v1.0/`, `v1.1/`)를 만들지 않습니다. 일반 설계 문서는 고정 파일명과 **Git Commit History**로 변경 사항을 추적합니다.
2. 운영 DB에 순서대로 적용하는 **마이그레이션 스크립트**는 예외적으로 식별 가능한 고유 파일명을 사용하고, 적용한 파일을 임의 수정하지 않습니다.
3. SQL 변경 시 영향을 받는 [요구사항](../requirements/README.md), [기획서](../planning/README.md), [기술 설계](../technical/README.md) 및 [OpenSpec](../../openspec/README.md)을 확인합니다.
4. 변경 내용은 작업 브랜치와 Pull Request에서 검토하고, 테이블 생성 가능 여부·제약조건·기존 데이터 영향 등을 확인한 뒤 승인합니다.
5. `main` 병합은 별도 승인 후 진행합니다. 실제 SQL 파일의 내용은 명시적 요청 없이 임의 수정하지 않습니다.

> 현재 이 폴더에는 관리 안내서만 있으며, 데이터베이스 스키마 파일이나 ERD가 생성·확정되었다는 의미는 아닙니다.
