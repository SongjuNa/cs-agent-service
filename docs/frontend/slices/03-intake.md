## 2. 구현 계획

| 무엇 | 어디 | 어떻게 |
|---|---|---|
| 화면 | `src/features/intake/IntakePage.tsx`, `intake.css` | 단계 표시 3개 + 단계별 카드. 예전 `src/IntakePage.tsx`를 옮겨 다시 만듦 |
| ① 문의 입력 | 같은 파일 `InputStep` | 시연용 고정 5건 목록 + 번호 직접 입력(`GET /gold/tickets/{id}`), 입력 6칸(채널·접수 시각·고객 ID·제품 코드·고객 언어·본문), "불러옴" 칩, "채점용 문의" 칩. 칸 오류는 서버 문구(`errors[].field·message`)를 칸 아래에 |
| ② 자동 처리 | `ProgressStep` | `POST /tickets`가 준 `run_id`로 `GET /runs/{id}/steps`, `GET /tickets/{id}`를 2초마다 읽음. 처리 단계(T2, Q1…)를 6줄로 묶어 끝난 줄 ✓, 지금 줄 회전, 실패 줄 ✕. 읽기 실패 3번 연속이면 안내 |

| 통화 녹음 칸 | `src/features/phone/CallPanel.tsx` | FR-050 통화 녹음 칸은 그대로 떼어 두고 채널이 전화일 때 입력 칸 사이에 보임. SCR-05 슬라이스에서 전화 상담 화면으로 옮김 |
| 시험 | `e2e/scr-01.spec.ts` | AC-3·AC-5는 실제로 접수(Gemini 호출). AC-4는 실패 상태라 응답을 흉내 냄 |

6줄 묶음(구현 선택, 기술 명세서 §4 노드 표): 언어 식별(T1) / 유형 분류와 요청 나누기(T2, T3) / 긴급도·제공 정보(Q1) / 규칙표(Q2~Q6, Q9a) / 문서 근거·숫자(Q8a, Q8, Q9) / 초안 작성과 자체 대조(Q7, Q10, Q11, T5, Q13, Q14, T6). T2가 언어 식별과 분류를 함께 해서 T2 기록이 생기면 첫 두 줄이 함께 넘어간다.

## 4. 수용 기준 확인

2026-10-29, 실제 API 위에서 SCR-01 시험 6개 통과. 슬라이스 1·3 시험 19개 함께 통과, 티켓 상세 읽기 시험 11개 다시 통과. 목은 AC-4(언어 모델 호출 실패)에만 썼다.

| AC | 결과 | 비고 |
|---|---|---|
| SCR-01-AC-1 | 통과 | 6칸 채움, 제목 칸 없음 |
| SCR-01-AC-2 | 통과 | 서버 문구 "고객 ID를 찾을 수 없음"이 칸 아래, ① 단계 그대로 |
| SCR-01-AC-3 | 통과(실제 접수) | ② 진행 표시 → ③ 티켓 번호·담당 부서(저압기기 기술지원) → [티켓 상세 보기] |
| SCR-01-AC-4 | 통과(목) | 실패 줄 ✕, "자동 처리 실패: T2", [티켓 상세에서 다시 처리]로 상세 이동 |
| SCR-01-AC-5 | 통과(실제 접수) | "펌웨어 P?, 매뉴얼 P?" 두 문의. 담당이 TS_LV가 아니라 안내 띠가 보임 |
| SCR-01-AC-6 | 통과 | 서버 문구 "내용을 입력하세요" |

### 확인하며 알게 된 것

- 처리 단계 기록은 단계가 끝날 때 쌓여서, 처음 몇 초는 첫 줄만 돌다가 T2가 끝나면 두 줄이 함께 넘어간다.
- 실제 접수 시험 2개가 돌 때마다 티켓이 DB에 남는다(슬라이스 2와 같음).
- 목업을 따른 곳(구현 선택): 3단계 마법사, ③ 단계에 머물고 [티켓 상세 보기](FR-001 처리 5 "상세로 이동"과 한 번 누르는 차이), 제목 안내 문구.
- 명세를 따른 곳(목업과 다름): 고객 언어 칸, 번호 직접 입력, 실제 단계 기록으로 진행 표시, 실패 표시.
- 넣지 않은 것: 제목·연락처 칸(화면 명세 영역 표에 없음, FR-003 처리 3). 예전 화면에 있던 두 칸은 뺐다.
