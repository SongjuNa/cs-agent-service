# requirements — 기능 요구사항 명세 관리

## 목적
해외고객향 C/S 대응 AI Agent 프로젝트의 **기능 요구사항(FR)**, 비기능 요구사항(NFR), 인수 기준 및 변경 이력을 추적합니다. 프로젝트 기획서는 [planning](../planning/README.md)에서, 구현 단위의 SDD 변경 명세는 [OpenSpec](../../openspec/README.md)에서 관리합니다.

## 현재 파일과 저장 위치

| 경로 | 역할 | 현재 상태 |
| --- | --- | --- |
| `functional-requirements.md` | 기능 요구사항 명세서 원본(현재 v1.5) | 등록됨 |
| `README.md` | 이 폴더의 운영·버전 관리 규칙 | 관리 문서 |
| `exports/` | HTML/PDF 열람·제출용 파일 보관 위치 | 디렉터리만 생성됨. HTML/PDF는 아직 없음 |

- 위 한국어 파일명은 **실제로 업로드된 파일명**을 표시합니다. Git에 등록된 원본 파일명·내용은 별도 요청 및 승인 없이 바꾸지 않습니다.
- Git의 `functional-requirements.md`가 편집 원본입니다(팀 Notion은 2026-10-20부터 쓰지 않음). 판 번호는 문서 머리 표와 커밋으로 관리합니다.

## 관리 원칙: 원본과 내보내기 파일

| 유형 | 역할 | 수정 규칙 |
| --- | --- | --- |
| Markdown (`.md`) | 해당 버전의 문서 내용 원본/보관본 | 변경이 필요하면 다음 버전에서 승인 후 반영 |
| `exports/functional-requirements.html` | 최신 버전의 브라우저 열람·제출용 파일(향후 생성 시) | 직접 내용 편집 금지. 승인된 원본을 기준으로 재생성 |
| `exports/functional-requirements.pdf` | 최신 버전의 인쇄·제출용 파일(향후 생성 시) | 직접 내용 편집 금지. 승인된 원본을 기준으로 재생성 |

1. **하나의 문서에 여러 편집 원본을 두지 않습니다.** Notion이 작업 원본인 동안에는 Notion의 최신 내용과 Git 보관본을 서로 독립적으로 수정하지 않습니다.
2. Git에서 문서를 관리하는 경우 **버전별 폴더 및 파일 복제**(`v1.0/`, `v1.1/`, `functional-requirements-v1.1.md` 등)를 만들지 않고, 같은 파일의 Git 커밋 이력으로 변경을 추적합니다. 현재 등록된 한국어 파일은 합의 없이 개명하지 않습니다.
3. 향후 HTML/PDF가 생기면 `exports/`에는 **최신 내보내기본만** 저장하고, 이전 공식 제출본은 GitHub Release에 버전 명시 파일로 보존할 수 있습니다.
4. 내보내기 결과물은 Markdown과 레이아웃·서식이 달라도 되지만, **요구사항 본문과 버전은 일치**해야 합니다. 업데이트하지 못한 이전 산출물을 최신 버전으로 표시하지 않습니다.
5. HTML/PDF/ZIP은 현재 제공되지 않았으므로 임의로 생성하지 않습니다. `exports/.gitkeep`은 최초 산출물 등록 시 삭제할 수 있습니다.
6. Markdown 원문의 문구·FR ID·완료 기준·표·메타데이터·링크는 임의 수정하지 않습니다. 오류가 있으면 별도로 보고하고 팀 승인 후 수정합니다.

## 요구사항 추적 및 변경 규칙

- 원문에 부여된 요구사항 ID(예: `FR-001`)를 유지하며, 기능 설명·입력·처리·출력·예외·완료 기준(Given-When-Then) 및 의존성을 추적합니다.
- 기능의 MVP/확장/제외 범위 및 결정 사항은 [프로젝트 기획](../planning/README.md)과 상호 대조하되, 원문의 불일치를 **자동 수정하지 않습니다**.
- 구현을 위한 구체적 변경은 [OpenSpec](../../openspec/README.md)의 작업 명세에 관련 FR ID를 연결합니다.
- API 계약이 확정되면 해당 OpenAPI 정의와 요구사항 사이의 불일치를 PR 검토 시 확인합니다.
- 요구사항 변경은 변경 이유 기록 → 영향 범위 검토 → 팀 검토·승인 → 해당 문서 버전 업데이트 → Git 커밋 순서로 진행합니다. AI 도구가 팀의 결정을 대신 확정하지 않습니다.

## Git 버전·검수 규칙

1. Git에 v1.0을 보관한 후 v1.1, v1.2 등을 반영할 때는 동일 경로의 파일을 수정하고 버전을 명시한 커밋 메시지를 사용합니다. 예: `docs: upgrade functional requirements to version 1.1`.
2. 이전 버전은 Git History에서 찾습니다. Git 태그는 개별 파일이 아니라 **저장소 전체의 특정 커밋**을 가리킵니다.
3. 작업은 별도 브랜치/Pull Request에서 검토하며 `main` 병합은 팀 승인 후 수행합니다.
4. HTML/PDF 생성 시 Markdown/Notion에서 내보낸 해당 버전과 문서 내용, 요구사항 ID, 표, 다이어그램, 페이지 표시, 한글, 링크 및 파일 크기·체크섬을 확인합니다.
5. 파일을 실제로 등록하기 전에는 README에 **업로드 완료**라고 표시하지 않습니다.
