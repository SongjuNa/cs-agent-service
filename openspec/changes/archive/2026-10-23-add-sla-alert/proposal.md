# Proposal: SLA 위험 경고 (add-sla-alert)

## Why

기한이 다가오거나 넘은 문의에 경고를 달아 접수함과 티켓 상세에 보이고, 접수함은 경고가 있는 문의를 위로 올린다(근거: 명세서 v1.5 FR-027 기능 설명, 처리 5). 10번 변경으로 SLA 두 시계와 자동 종료 함수가 생겼지만 주기적으로 부르는 곳이 없다(근거: 개발_결정_기록 변경 10 "범위 밖", 기술 명세서 v1.4 §6-4 주기 점검).

## What Changes

- **경고 점검 (`app/sla/alerts.py`)**: 기준 시각(as_of)에 끝나지 않은 문의(NEW, IN_PROGRESS, WAITING_CUSTOMER, ESCALATED)의 두 시계를 읽어, 조건을 처음 만족한 경고만 sla_alert에 넣는다(근거: 명세서 FR-027 처리 1~3, 기술 명세서 §6-4 주기 점검 1, schema.sql sla_alert UNIQUE(sub_ticket_id, alert_type)).
  - 해결 경과가 목표의 75% 이상이면 RES_AT_RISK, 넘으면 RES_BREACHED(근거: FR-027 처리 2, ref.sla_setting at_risk_threshold).
  - 1차 응답이 아직 없는 문의는 75% 이상 FR_AT_RISK, 넘으면 FR_BREACHED(근거: FR-027 처리 3).
  - WAITING_CUSTOMER 문의에는 해결 경고를 새로 달지 않는다(근거: FR-027 처리 4).
  - 발생 시각은 점검 시각이 아니라 조건을 넘은 실제 시각이다(근거: FR-027 예외 1행, §6-4 "received_at + 대기 + 목표 × 0.75").
  - SLA 미정 문의는 점검하지 않는다(근거: FR-027 예외 2행).
  - 목표가 늘어 조건이 풀린 경고에는 해제 시각을 쓴다(근거: FR-027 처리 6, §6-4).
- **주기 점검 (`app/scheduler.py`)**: 한 주기에 경고 점검 → 무응답 종료·해결 뒤 종료(10번의 `close_due`)를 차례로 한다. FastAPI 안에서 APScheduler로 5분마다 부른다(근거: 기술 명세서 §6-4 "APScheduler를 FastAPI 안에서 돌린다. 한 주기에 네 가지를 차례로", FR-027 처리 4 "같은 점검에서 무응답 168시간 종료를 함께"). 오류는 기록하고 다음 주기에 다시 한다(근거: FR-027 예외 3행).
- **상세 API**: 하위 문의마다 경고 이력(종류, 발생 시각, 경과, 목표, 해제 시각)을 더한다(근거: FR-027 출력 "티켓 상세에 경고 이력").
- **재생 채점**: 운영진 미해결 문의를 scoring 스키마에서 스냅샷 시점으로 점검해 정답 sla_resolution_status와 비교한다(근거: 명세서 AC-027-4, 기술 명세서 §10-1 3).

## Capabilities

### New Capabilities
- `sla-alert`: 경고 점검, 주기 점검 스케줄러, 상세의 경고 이력.

## 범위 밖

- **접수함 정렬과 경고 아이콘(FR-027 처리 5, AC-027-1의 "접수함 위쪽")**: 접수함(FR-029) 18번 변경. 뷰 svc.v_inquiry_inbox·v_ticket_summary는 이미 경고를 읽어 정렬 재료를 준다(근거: schema.sql 두 뷰, 2순위 변경 순서 18번).
- **우선순위 조정으로 생기는 경고(AC-027-5)**: 우선순위 조정(FR-028) 12번 변경에서 시험한다. 이번에는 목표가 바뀐 뒤 다시 점검하면 경고가 풀리거나 새로 생기는 부분만 만든다(근거: FR-027 처리 6, 2순위 변경 순서 12번).
- **회신 리마인드(주기 점검 2번, FR-023)**: 14번 변경에서 주기 점검에 붙인다(근거: §6-4 주기 점검 2, 2순위 변경 순서 14번).
- **경고 알림 대상(notified_to)**: 테이블 정의서에는 열("알린 대상")이 있지만 명세서에는 알림 기능이 없다(근거: 명세서 FR-027 출력, 테이블 정의서 4-9). 열은 비워 둔다(C-63).
- **접수함의 "SLA 미정" 표시(FR-027 예외 2행)와 정렬**: 18번 변경(근거: 2순위 변경 순서 18번).
- **우선순위 조정 때 바로 다시 점검(FR-028 처리 4)**: 12번 변경이 `raise_alerts`·`clear_alerts`를 조정 직후에 부른다. 이번에는 함수만 만든다(근거: 명세서 FR-028 처리 4).
- **실행 로그 보존 삭제(매일 1회, §6-5)와 주기 점검 오류의 실행 로그**: 처리 실행 로그(FR-036) 15번 변경(근거: 기술 명세서 §6-5, C-61).
- **AC-027-1의 "접수함 위쪽"과 AC-027-5**: 이번 시험은 경고 부분만 확인한다. 나머지는 18번·12번 변경 시험에서 한다(근거: CLAUDE.md 규칙 7).
- **티켓 상세 화면의 경고 표시**: 19번 변경(근거: 2순위 변경 순서 19번).

## Impact

- 새 파일: `backend/app/sla/alerts.py`, `backend/app/scheduler.py`, 시험 파일 (근거: 이 변경의 design 결정 1·3).
- 고치는 파일: `backend/app/main.py`(스케줄러 시작·멈춤), `backend/app/db/detail.py`(경고 이력), `backend/app/config.py`(스케줄러 켜기 설정), `backend/pyproject.toml`(apscheduler) (근거: 기술 명세서 §6-4 APScheduler).
- DB 구조는 고치지 않는다. sla_alert 표는 schema.sql에 이미 있다(근거: CLAUDE.md 규칙 4).
