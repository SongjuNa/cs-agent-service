# Proposal: 초안 만들기 (add-drafts)

## Why

고객에게 가는 글은 시스템이 초안(DRAFT)으로 만들고 상담원이 승인해 보낸다(근거: CLAUDE.md 규칙 3, 명세서 v1.5 FR-015·FR-021 기능 설명). 막는 정보가 있으면 정보 요청 초안을, 없으면 근거 절과 조회값만 쓴 답변 초안을 만든다. 상담원이 읽지 못하는 언어도 확인할 수 있게 한국어 대역을 붙인다(근거: FR-039 기능 설명). 이번 변경이 그 세 가지를 만든다(근거: 프로젝트 구조 1순위 판 6장 7번 `add-drafts` = FR-015, 021, 039).

## What Changes

- **처리 흐름을 그래프로 잇는다**: 5번 변경의 문의 이해(T1→T2→Q1) 뒤에 규칙 단계(Q2~Q6), 분기③(막는 정보), 6번 변경의 검색·조회(Q8·Q9), 분기④(근거 유무), 초안(Q7 또는 Q10), 자체 대조(Q11), 대역(Q13)을 LangGraph 그래프 하나로 잇는다(근거: 기술 명세서 v1.4 §1-2 처리 흐름 LangGraph, §2-1 하위 문의 그래프, §2-5 분기③④, 5번 변경 proposal "LangGraph 그래프는 7번 변경에서").
  - 1순위는 하위 문의 1개라 티켓 그래프의 병렬 실행(T3)과 답변 메일 구성(T5)은 만들지 않는다. 단일 문의의 답변 초안이 그대로 FINAL_REPLY 초안이다(근거: config.yaml "하위 문의 1개", 프로젝트 구조 1순위 판 4장, FR-021 처리 6). §2-1은 단일 문의도 T5를 지나는 같은 그래프로 그리므로, T5를 빼는 것은 1순위 범위에 따른 구현 선택이다.
  - 규칙 단계는 3번 변경의 함수를 그대로 부른다(근거: 3번 변경 openspec/specs/rule-engine).
- **정보 요청 초안 (FR-015, L3)**: 막는 항목이 있으면 고객 언어 메일 한 통을 만든다(근거: FR-015 처리 1~5, 에이전트 설계서 v1.1 4-5절).
  - 막는 항목은 "필수", 나머지 빠진 항목은 "가능하면"으로 나누고 영어 라벨을 괄호로 함께 쓴다(근거: FR-015 처리 2·3).
  - 막는 항목 라벨이 본문에 없으면 1회 다시 만들고, 그래도 없으면 본문 끝에 목록으로 덧붙인다(근거: FR-015 예외 2행).
  - L3가 실패하면 영어 고정 문구 F-1로 만들고 "자동 번역 실패"를 표시한다(근거: FR-015 예외 1행, 에이전트 설계서 부록 A F-1).
- **답변 초안 (FR-021, L4)**: 막는 항목이 없고 근거 후보가 있으면 근거 절 본문과 조회값만으로 고객 언어 답변을 쓴다(근거: FR-021 처리 1~4, 에이전트 설계서 4-6절).
  - 빠진 항목만 있으면 끝에 "가능하면 보내 주실 것" 한 줄을 넣는다(근거: FR-021 처리 1, 가-5).
  - 근거 후보가 없으면 초안을 만들지 않고 "근거 없음 — 상담원 작성 필요"를 표시한다(근거: FR-021 처리 2, AC-021-3).
  - 유형별 뼈대를 지시문에 넣는다(근거: FR-021 처리 4, 기술 명세서 §3-3 L4 뼈대 표).
- **자체 대조 (Q11, AC-017-5)**: 초안 속 인용이 모두 근거 후보 안에 있는지, 숫자와 날짜가 모두 허용 목록 안에 있는지 코드로 검사한다. 어긋나면 1회 다시 만들고, 다시 어긋나면 초안은 두고 어긋난 자리를 남긴다(근거: FR-021 처리 5, 기술 명세서 §3-4, 에이전트 설계서 6-1절). 언어 모델을 부르지 않으므로 `backend/app/checks/`에 둔다(근거: 프로젝트 구조 1순위 판 2장 checks/).
- **가린 값 유지 (AC-038-4)**: 초안과 대역에 든 가린 값(COMPANY_… 등)은 되돌리지 않고 그대로 둔다(근거: AC-038-4, 4번 변경 proposal "7번 변경에서 시험").
- **대역 (FR-039, L7)**: 초안마다 한국어 대역을 만든다. 인용·숫자는 원문 그대로 두게 하고, 원문과 대역의 인용·숫자 집합이 다르면 1회 다시 요청한다(근거: FR-039 처리 1~3, 기술 명세서 §3-2 L7, 에이전트 설계서 4-9절). 실패하면 대역 없이 "대역 없음(번역 실패)"을 표시하고 초안은 그대로 둔다(근거: FR-039 예외 1행).
- **지시문**: `prompts/l3_info_request_v1.md`, `l4_draft_v1.md`, `l7_gloss_v1.md`(에이전트 설계서 4-5·4-6·4-9 초안), `l4_category_skeletons_v1.md`(4-6절 뼈대 표)(근거: 에이전트 설계서 4-2절 3번).

## Capabilities

### New Capabilities
- `drafts`: 막는 정보 여부와 근거 유무에 따라 정보 요청 또는 답변 초안을 만들고, 코드로 대조하고, 대역을 붙이는 동작.

### Modified Capabilities
- 없음.

## 범위 밖

- **초안과 대역의 DB 저장(ticket_message DRAFT, message_gloss)과 AC-015-4**: 저장을 맡는 변경이 정해지지 않았다(개발_결정_기록 C-14). 이번에는 초안 객체를 돌려주기만 하고, 그 객체의 칸 이름을 svc.ticket_message·svc.message_gloss 열에 맞춘다(구현 선택).
- **AC-039-2(발송 뒤 SENT 본문), AC-039-4(임시 저장 뒤 새 대역)**: 승인·발송과 임시 저장(FR-031)은 9번 변경이다(근거: 프로젝트 구조 1순위 판 6장 9번).
- **AC-021-4(사람이 30건 대조)**: 사람이 하는 검수라 코드 시험으로 만들지 않는다(구현 선택. 팀 회의에서 검수 방법을 정한다, 개발_결정_기록 C 항목).
- **AC-021-5(팀 정답지 참고 점수)**: 팀 정답지 채점은 1순위 구조 밖이다(근거: 프로젝트 구조 1순위 판 4장).
- **AC-039-1의 "티켓 상세를 열면"**: 화면은 9번 변경이다. 이번에는 대역을 만드는 시점까지 시험한다(근거: 프로젝트 구조 1순위 판 6장 9번).
- **검토 표시 ①과 override_check(§3-4 4번)**: 상담원 화면·승인과 함께 9번 변경에서 한다(근거: 프로젝트 구조 1순위 판 6장 9번).
- **검증 에이전트(Q14, L8)**: 8번 변경이다(근거: 프로젝트 구조 1순위 판 6장 8번).
- **복합 문의 메일 구성(T5, L5), 고장 진단(Q8a), 이관 후보(Q9a), 상태 전이(T6)**: 2순위 이후다(근거: 프로젝트 구조 1순위 판 4장).
- **부서 회신 숫자 허용(가-6)**: 이관(FR-033)이 2순위라 부서 회신이 없다(근거: config.yaml).
- **하위 문의·티켓 시간 상한(120초·180초)과 동시 호출 수**: 서버에 올리는 변경으로 미룬다(구현 선택).

## Impact

- 새 파일: 지시문 4개, `backend/app/llm/drafts.py`(L3·L4·L7), `backend/app/checks/draft_check.py`(Q11), `backend/app/pipeline/graph.py`(그래프), `backend/app/pipeline/rules_step.py`(Q2~Q6), 시험 파일(근거: 프로젝트 구조 1순위 판 2장 pipeline/graph.py, llm/, checks/). 구조 2장은 노드를 `pipeline/nodes/`에 하나씩 두지만, 5번 변경의 `pipeline/understand.py`와 같은 방식으로 `pipeline/` 바로 아래에 둔다(구현 선택).
- 고치는 파일: `backend/pyproject.toml`에 `langgraph`(근거: §1-2), `openspec/config.yaml`의 규칙 두 줄을 따옴표로 감싼다. 감싸지 않으면 YAML이 그 줄을 글이 아닌 키·값으로 읽어 openspec이 proposal·design 규칙 전체를 무시한다(구현 선택. 내용은 그대로).
- 실제 언어 모델 시험은 `GEMINI_API_KEY`가 있을 때만 돈다(5번 변경과 같음, 구현 선택).
- DB 구조는 고치지 않는다.
