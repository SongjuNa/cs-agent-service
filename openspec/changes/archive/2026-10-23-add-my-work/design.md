# Design: 나의 업무 현황

## Context

FR-047은 1순위 사용자인 상담원의 대시보드다(근거: 명세서 v1.5 FR-047, D31). 값의 출처는 기술 명세서 §8-3이 정해 두었고, 숫자는 FR-026·027이 낸 값(inquiry_sla, sla_alert)을 세기만 한다(근거: §8-3 첫 문단). schema.sql은 이 화면용 뷰를 두지 않고 API가 계산한다고 적었다(근거: schema.sql 6장 머리 주석).

## Decisions

### 1. 집계 (`backend/app/db/workload.py`)

| 영역 | 값 | 근거 |
|---|---|---|
| 범위 | scope=mine이면 assignee_masked = 상담원 ID, scope=dept면 assigned_dept = 부서. 비우면 상담원이 있을 때 mine, 아니면 dept. 미해결(NEW·IN_PROGRESS·WAITING_CUSTOMER·ESCALATED)만 | §8-3 첫 문단, D33, FR-047 입력, 구현 선택 C-118 |
| 타일 ① 승인 대기 초안 | 보내지 않은 DRAFT·APPROVED 초안(superseded_at 비어 있음, 그 초안에서 나온 SENT 없음) 수. 접수함의 "승인 대기"와 같은 정의 | §8-3 타일 ①, FR-029 처리 2, 구현 선택 C-123 |
| 타일 ② 기한 위험·위반 | 아래 목록 행 수 | §8-3 타일 ② |
| 타일 ③·④ | 아래 두 목록 행 수 | §8-3 타일 ③·④ |
| 기한 위험·위반 목록 | 기준 시각에 살아 있던(그때까지 났고 풀리지 않은) 경고 4종이 있는 미해결 하위 문의, sla_id가 있는 것. 열: 문의 번호(복합이면 순번), 고객사·등급, 우선순위, 상태, 경고, 남은 시간(inquiry_sla(as_of).remaining_h, 음수 허용). 남은 시간 오름차순 | FR-047 처리 2, §8-3, 구현 선택 C-122 |
| SLA 미정 | 범위 안 미해결 중 sla_id가 빈 것의 수. 위험 목록에서 뺀다 | FR-047 예외 2행, §8-3 마지막 행 |
| 승인 대기 초안 목록 | 종류, 하위 문의, 만든 시각(초안의 sent_at_utc), 확인 표시 유무(그 초안이나 그 초안을 만든 실행에 실패한 self_check가 있음, VERIFY 제외). 우선순위 → 만든 시각 순 | FR-047 처리 3, §8-3, schema.sql ticket_message.sent_at_utc "초안은 만든 시각", 상세의 확인 표시(변경 19) |
| 고객 회신 대기 목록 | WAITING_CUSTOMER. 마지막 정보 요청 SENT 시각(없으면 상태 이력 INFO_REQUEST_SENT 시각), 경과, 126h·168h, 리마인드 SENT 여부. 경과가 긴 순 | FR-047 처리 4 ①, §8-3, FR-023, 구현 선택 C-119 |
| 이관 회신 대기 목록 | ESCALATED이고 escalated_to가 있는 것. 이관 시각 = 마지막 ESCALATE 이력, 경과. 경과가 긴 순 | FR-047 처리 4 ②, §8-3 |
| 오늘 처리 건수 | as_of 날짜(UTC), as_of까지 발송(AGENT·DEPT가 보낸 정보 요청·답변, D34) n, 이관(ESCALATE 이력) n, 조정(priority_adjustment) n. mine이면 내가 한 것(sent_by_name·changed_by·adjusted_by), dept면 그 부서 문의에 한 것 | FR-047 처리 5, §8-3, 구현 선택 C-120 |
| 빈 영역 | 영역별 문구("승인 대기 초안이 없습니다" 등) | FR-047 예외 1행 |
| 범위 없음 | 상담원도 부서도 없으면 "상단에서 이름과 부서를 고르세요" | FR-047 예외 3행 |

- schema는 svc 또는 scoring(재생 채점, 시험용). 접수함(`db/inbox.py`)과 같은 방식이다(근거: 변경 18 design 결정 1, 기술 명세서 §10-1).
- 언어 모델 호출 계층을 import하지 않는다(근거: CLAUDE.md 규칙 1·2).

### 2. API (`backend/app/api/me.py`)

- `GET /me/workload?dept=&scope=&as_of=`, 상담원은 `X-Agent-Id`. 부서는 접수함처럼 쿼리로 받는다(근거: §8-1 GET /me/workload 행, 변경 18 `GET /tickets?dept=`, 구현 선택).

### 3. 화면 (`frontend/src/MyWorkPage.tsx`, `/my`)

| 영역 | 내용 | 근거 |
|---|---|---|
| 범위 띠 | "{상담원} 담당 · {부서} · 기준 {as_of}" 또는 "부서 전체 기준", [내 담당]/[부서 전체](브라우저에 기억) | 화면 정의서 v1 SCR-04-01, ⑥ 부서만 선택, C-118 |
| 타일 4개 | 숫자 + 이름, 누르면 그 목록으로 스크롤 | 화면 정의서 v1 SCR-04-T1~T4, FR-047 처리 1 |
| 오늘 처리 | "발송 n · 이관 n · 조정 n", SLA 미정이 있으면 "SLA 미정 n건" | 화면 정의서 v1 SCR-04-N, SCR-04-X |
| 목록 4개 | SCR-04-L1~L4 열. 확인 표시는 노란 점, 고객 회신 대기는 126h 눈금 막대(끝이 168h) | 화면 정의서 v1 SCR-04-L1~L4 |
| 동작 | 행 클릭·Enter → 상세, 5분마다 갱신, 머리 막대(부서·기준 시각·상담원)를 바꾸면 다시 그림, 읽기 실패면 이전 값을 흐리게 두고 "불러오지 못함. 새로고침" | FR-047 처리 6·7, 예외 4행, SCR-04 ⑤·⑥, §8-2 |
| 메뉴 | 사이드바 "나의 업무 현황"을 켠다 | 화면 정의서 v1 SCR-00-05 |

### 4. 시험 (`backend/tests/acceptance/test_my_work.py`)

- AC-047-1·3: 운영진 4,000건을 scoring에 재생(롤백)하고 시험 코드만 정답 담당 부서를 넣는다. AC-047-3은 재생이 메시지를 만들지 않아 정보 요청·리마인드 행을 시험 준비로 넣는다(근거: CLAUDE.md 규칙 6 예외, 변경 18 시험 방식).
- AC-047-2·4·5·6: API로 접수(대역 언어 모델). 이관(FR-033, 3순위)은 시험 준비로 ESCALATE 전이만 한다(근거: openspec/config.yaml).
- AC-047-7: 우선순위 조정 시험의 문의(CSV1-000031, P4)를 경과 100h에 P3로 올린다(근거: AC-027-5, FR-028).
- 그 밖: 범위 없음, 빈 영역, 내 담당(assignee_masked), scope, SLA 미정(근거: FR-047 예외 1~3행, §8-3, C-118).

## Risks / Trade-offs

- C-118: 내 담당은 assignee_masked로 거른다. 새 접수 문의에 이 값을 채우는 기능은 명세서에 없고, 시연 재생은 정답지 값을 넣는다고 했지만(W6) 아직 재생 코드(jobs/replay_gold.py)가 넣지 않아 지금은 늘 비어 있다. 그래서 [부서 전체]로 바꿀 수 있게 scope를 두었다. 누가 언제 채울지는 팀이 정해야 한다(근거: 테이블 정의서 v1.3 assignee_masked "상담원이 맡으면 채운다", §8-3, D33).
- C-119: 재생 데이터에는 정보 요청 메시지 행이 없어, 발송 시각을 상태 이력 INFO_REQUEST_SENT 시각으로 대신한다. 서비스에서는 둘이 같은 순간이다. 발송·리마인드·이관 시각은 기준 시각(as_of) 이전 기록만 본다. 재생 데이터에는 스냅샷 뒤에 정보 요청이 나간 문의(CSV1-003951)가 있어, 그런 문의는 발송 시각·경과가 비어 보인다(근거: jobs/replay_gold.py, FR-025 처리 2, 화면 정의서 v1 SCR-00-04 "모든 조회의 as_of").
- C-120: 부서 전체일 때 "오늘 처리 건수"는 그 부서 문의에 누가 했든 센다. 명세서는 "이 상담원이" 한 것만 말한다(근거: FR-047 처리 5, 구현 선택).
- C-121: AC-047-1은 "해결 AT_RISK 8 + BREACHED 26 = 34, 타일 34"인데, 처리 2는 1차 응답 경고(FR_AT_RISK·FR_BREACHED)도 넣는다. 스냅샷 TS_LV에는 1차 응답 위험만 있는 CSV1-003951이 있어 타일은 35다. 처리 2대로 두고 시험은 34건이 모두 있는지와 35를 함께 본다(근거: FR-047 처리 2, AC-047-1, §8-3 확인 문장).
- C-122: 남은 시간은 해결 남은 시간(inquiry_sla.remaining_h)이다. 1차 응답 경고만 있는 문의도 해결 남은 시간으로 정렬된다(근거: §8-3 "inquiry_sla(as_of).remaining_h", 구현 선택).
- C-123: §8-3 타일 ①은 message_status = DRAFT라고 하지만 접수함 "승인 대기"와 같게 APPROVED와 진행 안내 초안도 센다(지금은 둘 다 만들어지지 않는다)(근거: §8-3, FR-029 처리 2, schema.sql v_inquiry_inbox has_unsent_draft).
- C-124: FR-047 입력은 "내 담당 = 담당 부서(D33 결정 전)"이고 기술 명세서 §8-3·테이블 정의서 T43은 assignee_masked다. §8-3을 따랐다(근거: FR-047 입력, §8-3, 테이블 정의서 v1.3 assignee_masked).
- C-125: 확인 표시는 FR-047 처리 3이 "확신 낮음·근거 없음·대조 불일치"를, §8-3·SCR-04-L2가 "self_check N 있음"을 말한다. 넓은 쪽(VERIFY 말고 실패한 검사 모두)을 따랐다(근거: FR-047 처리 3, §8-3, 화면 정의서 v1 SCR-04-L2).
- C-126: "SLA 미정 n건"은 링크가 아닌 칩이다(갈 목록이 없다). 로딩은 스켈레톤 대신 "읽는 중…"이다(근거: 화면 정의서 v1 SCR-04-X, ⑥, 구현 선택).
