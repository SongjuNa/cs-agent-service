# Proposal: 문의 이해 (add-inquiry-understanding)

## Why

규칙 엔진(3번 변경)은 문의 유형(category_code), 긴급도(urgency_flag), 제공 항목(provided_info)이 있어야 돈다. 이 값들은 고객 본문을 읽어 정해야 하므로 언어 모델이 맡는다(근거: config.yaml 설계 원칙 2 "언어 모델은 분류·긴급도·항목 추출", 기술 명세서 v1.4 §3-1 L1·L2). 이번 변경은 그 두 호출과, 호출 전후의 코드 검사를 만든다(근거: 프로젝트 구조 1순위 판 6장 5번 `add-inquiry-understanding` = FR-004, 005, 007, 008).

## What Changes

- **언어 모델 호출 계층 (Gemini)**: 모든 호출이 지나는 함수 하나를 `backend/app/llm/`에 둔다. 다음을 지킨다.
  - 구조화 출력(JSON 스키마, 코드값은 열거형)으로만 받는다(근거: 기술 명세서 §3-2, 에이전트 설계서 v1.1 4-2절 1번).
  - 호출 1회 시간 상한은 30초다. 시간 초과(LLM_TIMEOUT)나 스키마 위반(LLM_INVALID_OUTPUT)이면 1회 다시 부른다(근거: 기술 명세서 §2-4, §3-2, 에이전트 설계서 4-2절 2번).
  - 입력은 보내기 직전에 4번 변경의 `prepare_llm_input`을 지난다(근거: CLAUDE.md 규칙 2, 기술 명세서 §7).
  - 모델 이름은 환경 변수 `LLM_MODEL_SMALL`(기본 `gemini-3.8-flash`)로 정한다(근거: 기술 명세서 §1-5, §3-5, 에이전트 설계서 4-1절).
- **L1 문의 이해 (FR-004, 005, 007)**: 본문 언어, 문의 유형 10종, 긴급도 6값, 근거 문장, 영어 검색문을 한 번에 받는다(근거: 기술 명세서 §3-1 T24, 에이전트 설계서 4-3절).
  - 지시문은 `prompts/l1_understand_v1.md`로 둔다(근거: 에이전트 설계서 4-2절 3번, 4-3절).
  - 유형 정의와 긴급도 판단 기준은 팀 정답지 작성 기준서 v0.3의 1-1장과 2장을 넣는다(근거: 기술 명세서 §3-1 L1 입력, §3-3 "정답지와 같은 정의").
- **L2 제공 항목 추출 (FR-008)**: 항목 코드북 32개 중 본문에 값이 있는 항목을 원문 값, 정리 값, 위치와 함께 받는다(근거: 기술 명세서 §3-2 L2, 에이전트 설계서 4-4절). 지시문은 `prompts/l2_extract_v1.md`로 둔다.
- **코드 검사** (근거: 명세서 FR-004~008 처리·예외, 에이전트 설계서 4-3·4-4절 "코드 검사")
  - 확신도가 0.6 미만이면 "확신 낮음" 또는 "언어 판정 불확실"을 표시한다(근거: 기술 명세서 §3-6).
  - 긴급도 우선순서를 코드로 한 번 더 적용한다. L1이 요청을 둘 이상 돌려주면 모든 요청 중 가장 높은 긴급도를 하위 문의 1개에 쓴다(근거: FR-007 처리 3. 모든 요청에서 고르는 것은 안전 놓침을 막기 위한 구현 선택).
  - L2 결과는 코드북 밖 항목을 버리고 값을 정리한다(펌웨어 버전, 날짜, 수량, 제품 코드). 위치(span)를 확인하고, 에러 코드와 펌웨어 버전을 따로 복사한다.
  - 본문에서 찾은 제품 코드를 ref.product와 대조해 비어 있는 product_code를 채운다. 대조에 실패하면 "제품 미확정"을 표시한다(근거: FR-008 처리 4).
- **처리 흐름 앞부분 (T1 → T2 → Q1)**: 접수 입력을 받아 상태 객체(TicketState, SubTicketState)를 채우는 함수를 `backend/app/pipeline/`에 둔다(근거: 기술 명세서 §2-1·§2-2·§2-3, 4번 변경 proposal "범위 밖"의 body_masked·run FAILED·제목 제외).
  - 제목(inquiry_subject)은 상태 객체에 넣지 않는다(근거: 기술 명세서 §2-3, §3-3).
  - 가리기 검사 오류, 또는 L1이 시간 초과·오류로 두 번 실패하면 실행 상태를 FAILED로 둔다(근거: 기술 명세서 §2-2 T1·T2 행, 명세서 FR-005 예외 2행). L1이 코드값 밖 응답을 두 번 내면 값을 비우고 계속한다(근거: FR-004 예외 2행, FR-005 예외 1행, FR-007 처리 4). 두 갈래로 나눈 것은 구현 선택이며 문서끼리 달라 결정 기록에 남긴다.
  - 1순위에서는 하위 문의를 항상 1개 만든다(근거: config.yaml "문의는 항상 하위 문의 1개로 만든다").

## Capabilities

### New Capabilities
- `inquiry-understanding`: 고객 본문을 언어 모델로 읽어 본문 언어, 문의 유형, 긴급도, 제공 항목을 정하고, 코드로 검사해 상태 객체에 담는 동작.

### Modified Capabilities
- 없음.

## 범위 밖

- **팀 정답지 채점 (AC-004-4, AC-005-4, AC-007-4, AC-008-5)**: 팀 정답지 적재(W9)와 채점 배치(W4)를 1순위 구조에서 뺐다(근거: 프로젝트 구조 1순위 판 4장). AC-007-4 중 "운영진 데이터 4,000건으로 SAFETY·SITE_DOWN 재현율 보고"는 언어 모델을 4,000번 불러야 해서 키가 생긴 뒤 따로 돌린다(구현 선택, 결정 기록에 남김).
- **복합 문의 나누기 (FR-006)**: 2순위다(근거: config.yaml). L1 지시문(에이전트 설계서 4-3절)은 요청을 나누라고 하지만, 1순위에서는 첫 요청만 하위 문의 1개로 쓰고 나머지가 있으면 표시만 한다(구현 선택).
- **AC-005-1의 "FR-003으로 접수"와 AC-005-2의 "실행 로그에서 확인"**: 접수(FR-001·003)와 실행 로그(FR-036)는 2순위다(근거: 프로젝트 구조 1순위 판 4장). 이번에는 gold.v_inputs의 입력을 함수에 직접 넣고, 언어 모델에 실제로 보낸 글과 입력 항목 이름 목록에 제목이 없는지 확인한다.
- **AC-005-3의 "직접 선택 드롭다운"**: 화면은 9번 변경의 SCR-03M뿐이고 드롭다운은 없다(근거: config.yaml, 화면 정의서 v2 SCR-03M). 이번에는 category_code가 비고 "분류 실패"가 표시되는 것까지 확인한다.
- **AC-005-1의 CSV1-000031 (조장 확인 필요)**: 본문은 "notas de versión del firmware"(펌웨어 릴리스 노트) 요청이다(근거: tickets.csv CSV1-000031 본문). 명세서 AC-005-1과 운영진 값은 MANUAL인데, L1에 넣는 기준서 v0.3 1-1장은 릴리스 노트 요청을 FW_UPDATE로, MANUAL은 "릴리스 노트는 제외"로 정의한다. 시험은 명세서대로 MANUAL을 기대하되, 다르게 나오면 이 충돌로 기록한다.
- **FR-007 예외 "기한 경과" 표시와 입력 received_at**: L1 출력 스키마(기술 명세서 §3-2)에 기한 날짜 칸이 없고 L1 지시문(에이전트 설계서 4-3)에 접수 시각 자리가 없어서 지금 만들 방법이 정해져 있지 않다. 조장 확인이 필요하다.
- **영어가 아닌 반품 문의의 반품 사유 판정 시험(개발_결정_기록 C-4)**: 키가 있어야 L2를 돌릴 수 있어 키가 생긴 뒤 한다(구현 선택).
- **FR-005 예외 1행 "규칙 단계를 건너뛰고 상담원에게"**: 이번에는 category_code를 비우고 "분류 실패"를 표시하는 데까지 한다. 규칙 엔진은 유형이 비면 이미 "분류 뒤 계산됨"으로 멈춘다(근거: 3번 변경 openspec/specs/rule-engine). 둘을 잇는 일은 처리 흐름을 잇는 변경에서 한다.
- **결과를 DB(svc.ticket, svc.sub_ticket, svc.agent_run)에 저장하기**: 접수 API(`POST /tickets`)와 함께 만든다(근거: 기술 명세서 §2-4 실행 시작). 1순위 변경 목록에 접수 API를 맡는 변경이 따로 없어, 어느 변경이 저장을 맡을지는 조장 확인이 필요하다.
- **LangGraph 그래프**: 노드가 셋뿐이라 이번에는 함수로 잇고, 분기가 생기는 7번 변경(정보 요청/답변 분기③)에서 그래프로 옮긴다(구현 선택. 근거: 기술 명세서 §1-2 기술 스택, §2-5 분기).
- **동시 호출 수 상한 4(`LLM_MAX_CONCURRENCY`)**: 기술 명세서 §2-4가 요구하지만, 이번 변경은 한 번에 문의 하나만 처리하므로 처리 흐름을 서버에 올리는 변경으로 미룬다(구현 선택).

## Impact

- 새 파일: `prompts/l1_understand_v1.md`, `prompts/l2_extract_v1.md`, 그리고 `{category_definitions}`·`{urgency_codebook}` 자리에 넣을 글을 따로 둔 `prompts/l1_category_definitions_v1.md`, `prompts/l1_urgency_criteria_v1.md`(파일을 나눈 것은 구현 선택), `backend/app/llm/`의 호출 모듈, `backend/app/pipeline/state.py`와 처리 함수, 시험 파일(근거: 기술 명세서 §3-3 prompts/, 프로젝트 구조 1순위 판 2장).
- 고치는 파일: `backend/pyproject.toml`(Gemini 라이브러리 `google-genai`), `.env.example`(`LLM_MODEL_SMALL`), `backend/app/config.py`(근거: 기술 명세서 §1-5 환경 변수).
- 시험에는 `GEMINI_API_KEY`가 있어야 한다. 키가 없으면 언어 모델을 실제로 부르는 시험은 건너뛰고 그 사실을 결과에 보인다(구현 선택).
- DB 구조는 고치지 않는다.
