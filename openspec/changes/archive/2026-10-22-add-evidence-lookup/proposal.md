# Proposal: 근거 문서 검색과 숫자 조회 (add-evidence-lookup)

## Why

답변 초안(FR-021)은 근거 후보 안의 문서 절과 표에서 읽은 숫자만 쓴다(근거: 명세서 v1.5 FR-016 기능 설명, FR-017 기능 설명). 그래서 초안보다 먼저 문서 색인, 절 검색, 숫자 표 조회가 있어야 한다(근거: 프로젝트 구조 1순위 판 6장 6번 `add-evidence-lookup` = W2, FR-016, 017).

## What Changes

- **문서 색인 (W2)**: docs/ 107개 문서를 절 단위 청크로 나눠 `ref.doc_chunk`에 넣고 임베딩을 채운다(근거: 기술 명세서 v1.4 §4-2, §4-5, §9 W2).
  - `##` 또는 `###` 머리글 하나가 청크 하나다. 청크 ID는 `{doc_id}§{절 번호}`이고 절 번호는 글자로 보존한다(근거: §4-2).
  - 임베딩 입력은 문서 제목과 절 제목을 앞에 붙인 글이다(근거: §4-2).
  - 임베딩 모델은 환경 변수 `EMBEDDING_MODEL`(기본 `gemini-embedding-2`)로 정한다(근거: §1-2, §1-5, 에이전트 설계서 v1.1 4-1절).
  - 완료 확인: tickets.csv 4,000건 정답의 (reference_doc_id, reference_section) 쌍이 모두 청크 ID로 있다(근거: §4-2, §9 W2).
  - 실행은 `jobs/build_doc_index.py`로 한다(근거: 프로젝트 구조 1순위 판 2장 jobs/build_doc_index.py).
- **임베딩 호출**: 언어 모델 호출 계층(`backend/app/llm/`)에 둔다. 보내기 전에 `prepare_llm_input`을 지나고, 실패하면 1회 다시 부른다(근거: CLAUDE.md 규칙 2, 기술 명세서 §1-2 "호출부는 LLM 호출 계층 한 곳", FR-016 예외 2행). 1회 30초 상한을 임베딩에도 쓰는 것은 구현 선택이다(§2-4는 언어 모델 호출 기준).
- **문서 근거 검색 (FR-016)**: `backend/app/retrieval/`에 둔다(근거: 프로젝트 구조 1순위 판 2장 retrieval/).
  - 꼬리표로 범위를 먼저 좁힌다. 그 제품의 문서, 정책 4개, 그 제품군 FAQ만 본다(근거: FR-016 처리 1, §4-4 1번). 명세서는 제품 문서를 DS·IG·TG·RN으로 적었고 기술 명세서는 그 제품의 모든 문서(MG 포함, MANUAL 우선 종류에 MG)로 적었다. 기술 명세서를 따르고 결정 기록에 남긴다.
  - 유형별 우선 문서 종류를 먼저 검색하고, 없으면 범위 전체로 넓힌다(근거: FR-016 처리 2, §4-4 2번).
  - 검색문은 L1의 영어 검색문(query_en, 5번 변경 상태 객체)이다. 원문 문장은 쓰지 않는다(근거: §4-3 결정 전 진행 방식 A).
  - 점수는 코사인 유사도에 정확 문자열 가점 0.2를 더한 값이다. 에러 코드나 펌웨어 버전이 든 절에 가점을 준다(근거: FR-016 처리 3, §4-4 3번).
  - 최대 5개를 근거 후보로 돌려주고, 후보가 없으면 "근거 없음"을 표시한다(근거: FR-016 처리 4·5, §4-4 4·5번, §2-2 Q8 "≤ k개").
- **숫자 표 조회 (FR-017)**: `backend/app/retrieval/`에 둔다.
  - 유형별로 가격·납기·MOQ·합계, 사양값, 접수 시점 최신 펌웨어와 판정, 보증 기간을 표에서 읽는다(근거: FR-017 처리 1~3, 기술 명세서 §5-5).
  - 모든 값에 출처(표 이름, 행 식별자)를 붙인다(근거: FR-017 처리 4).
  - 버전은 점으로 나눈 숫자 묶음으로 비교한다. 할인가·납기 가산은 계산하지 않는다(근거: §5-5, D14).
  - 제품은 있는데 표에 행이 없으면 "표에 없음"을 표시한다(근거: §2-2 Q9 실패 칸).
- **처리 흐름 연결**: 5번 변경의 상태 객체에서 doc_candidates와 lookups를 채우는 함수를 둔다(근거: 기술 명세서 §2-2 Q8·Q9 행, §2-3 doc_candidates·lookups).

## Capabilities

### New Capabilities
- `evidence-lookup`: 문서를 절 단위로 색인하고, 문의에 맞는 근거 절과 표의 숫자를 찾아 상태 객체에 붙이는 동작.

### Modified Capabilities
- 없음.

## 범위 밖

- **팀 정답지 채점(AC-016-4, AC-017-4)**: 팀 정답지 적재(W9)와 채점 배치(W4)가 1순위 구조에 없다(근거: 프로젝트 구조 1순위 판 4장).
- **AC-017-5 (초안 숫자 대조)**: 초안을 만드는 7번 변경(FR-021)과 자체 대조(§3-4)에서 시험한다(근거: 프로젝트 구조 1순위 판 6장 7번).
- **"관련성 낮음" 표시와 기준 점수**: 기준 점수(T27)가 정해지지 않았다. 정해지기 전에는 후보가 비었을 때만 "근거 없음"으로 본다(근거: 기술 명세서 §4-4 5번).
- **다국어 임베딩(방식 B) 비교**: 개발하면서 팀 정답지로 비교하기로 했다(근거: §4-3, 다-18).
- **고장 진단(FR-018)과 증상 임베딩**: 1순위 범위 밖이다(근거: 프로젝트 구조 1순위 판 4장 Q8a).
- **결과 DB 저장(sub_ticket.evidence_json, reference_doc_id)**: 5번 변경과 같이 저장을 맡는 변경이 정해지지 않았다(개발_결정_기록 C-14).
- **화면의 "근거" 탭과 "표에서 읽은 값" 표**: 9번 변경(SCR-03M)에서 한다(근거: 프로젝트 구조 1순위 판 6장 9번).
- **검색 서비스 동시 호출 수 상한**: 5번 변경과 같이 미룬다(구현 선택).

## Impact

- 새 파일: `jobs/build_doc_index.py`, `backend/app/retrieval/`의 청크 나누기·검색·숫자 조회 모듈, `backend/app/llm/`의 임베딩 모듈, 시험 파일(근거: 프로젝트 구조 1순위 판 2장).
- 고치는 파일: `.env.example`와 `backend/app/config.py`에 `EMBEDDING_MODEL`(근거: §1-5). `jobs/load_reference.py`는 기준정보를 다시 넣기 전에 `ref.doc_chunk`를 먼저 비운다. 청크가 `ref.document`를 가리켜 기준정보를 다시 넣을 수 없기 때문이다(구현 선택. 색인은 그 뒤 W2로 다시 만든다, 기술 명세서 §1-5 초기화 순서).
- 실제 임베딩에는 `GEMINI_API_KEY`가 있어야 한다. 키가 없으면 실제 임베딩 시험은 건너뛴다. 검색 규칙 시험은 정해진 벡터를 내는 대역 임베딩으로 돌린다(구현 선택).
- DB 구조는 고치지 않는다. `ref.doc_chunk`의 열을 그대로 쓴다(근거: schema.sql).
