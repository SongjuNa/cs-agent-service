# Proposal: 티켓 상세 최소판 (add-ticket-detail-minimal)

## Why

1순위 18개 기능 중 근거 표시(FR-024), 초안 수정·승인·발송(FR-031), 대역 표시(FR-039)는 상담원이 보는 화면 기능이다. 그래서 티켓 상세 화면을 이 영역만 있는 최소판(SCR-03M)으로 만든다(근거: 프로젝트 구조 1순위 판 1장 1번, 화면 정의서 v2 0-1절). 화면이 읽을 값이 DB에 있어야 하므로, 지금까지 객체로만 돌려주던 처리 결과(개발_결정_기록 C-14, C-30)를 접수 API가 저장한다(근거: 기술 명세서 v1.4 §2-4 "POST /tickets가 … 저장하고 … 파이프라인은 서버 안의 백그라운드 작업으로 돈다", 프로젝트 구조 1순위 판 2장 api/tickets.py). 이번 변경이 1순위의 마지막 변경이다(근거: 프로젝트 구조 1순위 판 6장 9번 `add-ticket-detail-minimal` = FR-024, 031).

## What Changes

- **접수와 저장 (`POST /tickets`, `app/db/`)**: 접수 입력을 검사하고(미등록 고객 거부) 티켓·하위 문의(seq 1)·INQUIRY 메시지·접수 이력(INTAKE)을 한 트랜잭션으로 저장한 뒤 ticket_id를 돌려주고, 처리 흐름을 백그라운드로 돌린다(근거: 기술 명세서 §2-4 실행 시작, §8-1 `POST /tickets` "미등록 고객 거부, D25", 명세서 FR-001 D25·AC-001-2).
  - 처리가 끝나면 하위 문의 결과 열, 제공 항목(inquiry_field), 초안(ticket_message DRAFT), 대역(message_gloss), 자체 검사(eval.self_check: DRAFT_CHECK, 확인 표시, VERIFY), 실행 기록(agent_run, agent_step)을 저장한다(근거: 기술 명세서 §6-2 표 목록, §5-7 읽는 값, 테이블 정의서 v1.3).
  - INQUIRY 본문은 원문 그대로 저장하고 가린 곳 수를 mask_count에 남긴다. 실행 기록(agent_step)에는 가린 글만 넣는다(근거: 명세서 FR-038 처리 3, AC-038-1, 기술 명세서 §7, 4번 변경 proposal "원문 저장과 mask_count 기록").
- **상세 API (`GET /tickets/{id}`)**: 티켓 머리, 하위 문의 판단값과 근거(규칙 판정 과정 포함), 초안·대역, 검토 표시 5개(review_marks), 처리 중 여부를 한 묶음으로 돌려준다(근거: 기술 명세서 §8-1, §5-7, 화면 정의서 v2 SCR-03M ④). 검토 표시는 저장하지 않고 읽을 때 계산한다(근거: §5-7).
- **절 본문 (`GET /chunks/{chunk_id}`)**: 인용을 누르면 절 본문을 연다(근거: §8-1, FR-024 처리 3, AC-024-2).
- **초안 다루기 (`PUT /messages/{draft_id}`, `POST …/gloss`, `POST …/verify`, `POST …/send`)**:
  - 임시 저장은 DRAFT 본문만 바꾸고, 고친 본문을 코드로 다시 대조하고(구현 선택: ①을 최신으로 두려고), 대역을 다시 만든다. 검증은 다시 부르지 않고 ⑤는 "고친 뒤 검증 안 함"(STALE)이 된다(근거: §8-1, 명세서 FR-031 처리 7, 에이전트 설계서 v1.1 4-10절 "다시 도는 때", 추가 결정 가3).
  - [다시 만들기]와 [다시 검증]은 대역(L7)과 검증(L8)을 1회 더 부르고 새 행으로 남긴다(근거: §8-1, FR-039 예외 1행, FR-049).
  - 승인·발송은 최종 본문을 초안 종류에 맞게 다시 대조하고(답변은 인용·숫자, 정보 요청은 막는 항목 라벨. 근거: FR-031 처리 2, 에이전트 설계서 6-1 3번), 불일치·⑤ 지적·남은 막는 항목이 있으면 409와 목록을 돌려준다. override_check = true로 다시 보내면 SENT 행을 새로 쓰고, 초안을 APPROVED로 바꾸고, 처음이면 1차 응답 시각을 기록한다(근거: 명세서 FR-031 처리 1·2·3·5, 예외 표, §8-1 send, FR-049 처리 5).
- **화면 (`frontend/`, SCR-03M)**: React + Vite + TypeScript로 티켓 상세 최소판 한 화면과 팝업 4개(P1 "왜?", P2 절 본문·조회값 출처, P7 발송 전 확인, P8 실패 안내)를 만든다. 레이아웃은 A안 사이드바형이다(근거: 화면 정의서 v2 0-7절, SCR-03M, 기술 명세서 §1-2 기술 스택).
- **문의 넣기 (`jobs/run_tickets.py`)**: 정답지 문의의 입력 열만(gold.v_inputs) 골라 `POST /tickets`로 넣는다(근거: 프로젝트 구조 1순위 판 2장 jobs/run_tickets.py, 화면 정의서 v2 0-2절, CLAUDE.md 규칙 6).

## Capabilities

### New Capabilities
- `ticket-detail`: 접수 저장, 상세 묶음과 검토 표시, 초안 임시 저장·대역·검증·승인 발송, 티켓 상세 최소판 화면.

### Modified Capabilities
- 없음. 처리 흐름(drafts, verification)은 그대로 부르고 결과를 저장만 한다(구현 선택).

## 범위 밖

- **상태 전이(FR-025)와 SLA 다시 계산(FR-026)**: 발송 뒤 WAITING_CUSTOMER·RESOLVED 전이와 처리 끝 IN_PROGRESS 전이를 하지 않는다. 접수 이력(INTAKE → NEW)만 남긴다(근거: config.yaml "FR-031은 메시지 이력에 발송 행을 쓰고 1차 응답 시각을 기록하는 데까지", 프로젝트 구조 1순위 판 4장 "T6 상태 전이 … FR-025 2순위"·5장, 화면 정의서 v2 0-1절). 그래서 AC-031-1·AC-031-2의 상태 부분은 시험하지 않는다(근거: 화면 정의서 v2 SCR-03M ⑧ "AC-031-1·2의 발송 행·1차 응답 시각 부분", 개발_결정_기록 C-37).
- **AC-031-6(예외 부서 메일)**: 이관(FR-033)이 3순위다(근거: 명세서 기능 목록 "FR-033 MVP 3순위").
- **실행 로그 화면과 오류 집계(FR-036)**: 2순위다. 다만 "왜?"(FR-024)가 읽는 agent_step 행은 저장한다(근거: 명세서 기능 목록 "FR-036 MVP 2순위", 화면 정의서 v2 CP-3·C-02~C-04·P1 출처 agent_step.output_json. 구조 문서 4장 "1순위에서는 서버 로그로 충분"과 다르다, 개발_결정_기록 C-38).
- **고장 진단 후보(FR-018)·이관 후보(FR-020) 줄**: 3순위라 최소판에 없다(근거: 화면 정의서 v2 0-1절, SCR-03M ⑦ AC-024-1).
- **접수 시뮬레이터·접수함·나의 업무 현황, 판단값 수정, 고객 원문·이력 탭**: 2순위다(근거: 화면 정의서 v2 0-1절, 0-7절). [다시 처리]도 2순위다(근거: 화면 정의서 v2 SCR-03M ⑥).
- **보낸 사람 연락처(AC-038-7)**: 접수 입력에 연락처 열을 받지 않는다(근거: 개발_결정_기록 C-8, AC-038-7 범위 밖).
- **초안이 없을 때 상담원 직접 작성(화면 정의서 R-06), 대역 언어 영어 전환(FR-039 입력), 발송 전 언어 불일치 경고(FR-031 처리 1)**: 새 초안 행을 만드는 API·영어 대역·본문 언어 판정이 더 필요해 미룬다(개발_결정_기록 C-44).
- **부서 회신 숫자 허용, 복합 문의 여러 구역**: 이관(3순위)·복합 문의(2순위)가 없다(근거: config.yaml, 명세서 기능 목록).
- **하위 문의 120초·티켓 180초 상한, 서버 전체 동시 호출 수 4**: 기술 명세서 §2-4에 정해진 값이지만 이번 변경에서는 넣지 않고 서버에 올리는 변경으로 미룬다(범위 결정, 7번 변경과 같음).

## Impact

- 새 파일: `backend/app/api/tickets.py`, `messages.py`, `chunks.py`, `jobs/run_tickets.py`, `frontend/`(근거: 프로젝트 구조 1순위 판 2장). `backend/app/db/store.py`(저장), `detail.py`(상세 묶음·검토 표시), `backend/app/api/deps.py`, 시험 파일은 구현 선택이다(구조 2장은 `db/` 폴더만 둔다).
- 고치는 파일: `backend/app/main.py`(라우터), `backend/app/pipeline/graph.py`(필수정보 결과·근거 절·LLM 입력 항목 이름을 실행 결과에 남김)(구현 선택).
- DB 구조는 고치지 않는다. 표·열은 테이블 정의서 v1.3 그대로 쓴다(근거: CLAUDE.md 규칙 4).
