# Proposal: 우선순위 조정과 SLA 재계산 (add-priority-override)

## Why

상담원은 규칙으로 정해진 우선순위를 사유를 적고 바꿀 수 있어야 하고, SLA 목표는 바뀐 우선순위로 다시 정해져야 한다(근거: 명세서 v1.5 FR-028 기능 설명, config.yaml 설계 원칙 6). 운영진 데이터의 조정 120건은 모두 조정된 우선순위 기준 목표다(근거: FR-028 기능 설명 "120/120").

## What Changes

- **조정 (`app/sla/adjust.py`)**: 하위 문의의 최종 우선순위를 새 값으로 바꾸고 조정 표시를 켠다. 규칙 결과(priority_rule_id)는 그대로 둔다(근거: FR-028 처리 2).
  - FR-014의 SLA 목표 조회를 새 우선순위로 다시 돌려 sla_id와 목표 두 개를 덮어쓴다(근거: FR-028 처리 3, FR-014 처리 5, 기술 명세서 §5-4 "조정 때는 다시 조회해 덮어쓰고").
  - 바로 그 문의의 경고를 다시 점검한다(11번의 raise_alerts·clear_alerts). 경과 시간은 바꾸지 않는다(근거: FR-028 처리 4, 화면 정의서 v1 SCR-03-P3 "경고 재평가").
  - priority_adjustment에 한 줄을 남긴다: 시각, 상담원, 이전·새 우선순위, 이전·새 sla_id와 목표, 사유 분류, 사유(근거: FR-028 처리 5·6, schema.sql priority_adjustment).
  - 거부: 같은 우선순위("현재와 같은 우선순위"), 사유 없음("조정 사유를 입력하세요"), 종료 문의("종료된 문의는 바꿀 수 없음")(근거: FR-028 처리 1, 예외 1·2행, 화면 정의서 v1 SCR-03-P3 오류 문구). 응답 코드 400·409를 나눈 것은 구현 선택이다.
  - 조정하면 바로 위반(BREACHED)이 되는 경우 "이 조정으로 SLA 위반 상태가 됩니다. 계속할까요?"를 돌려주고, 상담원이 확인하면 반영한다(근거: 화면 정의서 v1 SCR-03-P3 미리 보기). 명세서 FR-028 예외 3행은 "그대로 반영하고 확인 창 표시"라서 두 문서가 다르며, 화면 정의서 쪽을 골랐다(C-65). 문구는 명세서 "SLA 위반"을 따르고 화면 정의서 v1의 "기한 위반"과 다르다(C-66).
- **API**: `POST /sub-tickets/{sub_ticket_id}/priority`(조정)와 `GET /sub-tickets/{sub_ticket_id}/priority?new_priority=`(미리 보기)(근거: 기술 명세서 §8-1 POST 행. GET 미리 보기는 화면 정의서 v1 P3 "미리 보기"를 위한 구현 선택이며, 기술 명세서 §8-1과 화면 정의서 v1 부록 A 어디에도 없는 주소다).
- **상세 API**: 하위 문의마다 조정 표시와 조정 이력을 더한다(근거: FR-028 출력 "최종 우선순위, 조정 표시, 새 SLA 목표, 다시 판정한 SLA 상태, 변경 이력").

## Capabilities

### New Capabilities
- `priority-override`: 우선순위 조정, 목표 재조회, 경고 재점검, 조정 이력, 미리 보기.

## 범위 밖

- **조정 화면(SCR-03-P3)과 C-03·C-06 표시**: 티켓 상세 전체판 19번 변경(근거: `bootcamp/openspec/2순위_시작_전후비교.md` 결정 2의 변경 순서 19번). 조정 결과의 "이력 1줄"(화면 정의서 v1 P3 결과, 기술 명세서 §8-1 `/timeline`의 조정 줄)도 19번에서 한다(근거: 같은 순서표 19번).
- **AC-028-3의 팀 정답지 채점과 조정 재생**: 명세서 AC-028-3은 팀 정답지(D30)에서 조정을 재생해 채점하라고 하고, 기술 명세서 §10-1 1·3번은 4,000건에서 정답 우선순위로 목표를 조회하라고 한다. 팀 정답지가 DB에 없어 운영진 데이터의 조정 120건으로 목표 조회만 확인한다(C-67)(근거: 명세서 AC-028-3, 기술 명세서 §10-1 1·3번).
- **"오늘 처리 건수"의 조정 n**: 나의 업무 현황 20번 변경(근거: 기술 명세서 §8-1 현황 표, `2순위_시작_전후비교.md` 결정 2의 변경 순서 20번).
- **우선순위가 빈 문의를 조정으로 채우기**: 명세서는 허용하지만(FR-011 예외 1행, FR-014 예외 1행) priority_adjustment.from_priority가 NOT NULL이라 표를 고쳐야 한다. 이 변경은 거부하고 사람에게 묻는다(C-68)(근거: CLAUDE.md 규칙 4, schema.sql).
- **흐름을 다시 돌릴 때 조정값 보존**: 다시 처리하는 기능이 아직 없다. 흐름을 다시 돌리는 첫 변경에서 지킨다(C-69)(근거: FR-011 예외 3행).

## Impact

- 새 파일: `backend/app/sla/adjust.py`, `backend/app/api/sub_tickets.py`, 시험 파일(근거: 이 변경의 design 결정 1·2).
- 고치는 파일: `backend/app/sla/alerts.py`(문의 번호로 좁혀 점검), `backend/app/db/detail.py`(조정 이력), `backend/app/main.py`(라우터) (근거: design 결정 1·3).
- DB 구조는 고치지 않는다. priority_adjustment 표는 schema.sql에 이미 있다(근거: CLAUDE.md 규칙 4).
