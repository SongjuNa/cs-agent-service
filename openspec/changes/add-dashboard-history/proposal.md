# Proposal: 운영 대시보드용 해결·종료 이력 적재 (add-dashboard-history)

## Why
최신 목업의 운영 대시보드(일별 접수 추이, 부서별 병목, 상담원별 업무량, 기한 충족률)와 "내 실적"을 실제 값으로 그리려면 해결·종료된 문의가 필요하다. 서비스 DB에는 미해결 360건과 시험 접수본뿐이라 접수일이 32일에만 있고 해결된 문의가 거의 없어(406건 중 40건) 그래프가 비어 보인다. 원본 정답지에는 4,000건이 12개월(2025-10 ~ 2026-09)에 고르게 있다. 조작한 날짜가 아니라 **실제 이력을 적재**하는 것이 정직한 해법이다.

## What Changes
- `jobs/replay_history.py`: 정답지의 해결·종료(RESOLVED·CLOSED) 문의를 svc에 재생한다(약 3,635건, 팀 정답지 문의는 제외). 변환 방식(이력 이벤트, 메시지, SLA 목표)은 기존 미해결 재생(`jobs/replay_demo.py`)과 같다. 250건씩 트랜잭션을 나눠 넣고, 이미 있는 번호는 건너뛴다. Gemini를 부르지 않는다.
- `jobs/replay_demo.py`: `replay(conn, statuses, limit)`로 상태와 건수 제한을 받게 했다(기본값은 기존과 같음).
- **DB 구조 변경 없음.** 서비스 코드(`backend/app`) 변경 없음.

## ⚠️ 규칙 변경 (팀 보고용)
- **규칙 6의 예외를 넓힌 것:** 조장 결정(2026-10-29, 1안)은 "미해결 360건을 넣는 적재 작업만 정답 열을 읽는다"였다. 이 작업은 해결·종료 건까지 읽는다(최신 목업 기준 + 사용자 허락 2026-10-31, 나중에 정리 보고). 서비스 실행 코드는 계속 `gold.v_inputs`만 읽는다.

## 영향 (측정)
- 적재 3,635건: **20초 안에** 끝난다.
- 접수함 응답 약 0.07초 → 0.35초(최초 호출 0.76초), 나의 업무 현황 0.03 → 0.06초. 사용에는 문제없으나, 접수함 SLA 계산이 문의 전체를 훑는 구조라 건수가 더 늘면 느려질 수 있다.
- 기본 접수함(종료 건 숨김)의 건수는 그대로다(TS_LV 미해결 79건).
- 접수함 화면 시험 2개(SCR-02-AC-8, AC-11)는 응답이 느려지며 "이전 목록을 읽는" 타이밍 문제가 드러나 새 목록을 기다리도록 고쳤다.

## 범위 밖
- 운영 대시보드·내 실적 화면과 집계 API(다음 변경). 접수함 SLA 계산 최적화.

## 이미 만들어진 DB에서 쓰는 방법
`python -m jobs.replay_history` (저장소 루트, gold 적재 후). 되돌리려면 `DELETE`가 아니라 DB를 다시 만든다(svc 이력은 삭제를 거부한다).
