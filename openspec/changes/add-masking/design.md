# Design: 개인정보 가리기

## Context

동기는 proposal.md의 Why를 본다. 따를 기준은 다음과 같다.

- 명세서 v1.5 FR-038 처리 1~7, 예외, AC-038-1~7(근거: docs/requirements/functional-requirements.md).
- 기술 명세서 v1.4 §7(위치, 검사식, 제외 목록, 검사 오류), §6-5(실행 로그에 넣는 글은 모두 가린 글, 오류 종류), §3-3(고객 본문은 `<customer_message>` 안에만)(근거: docs/technical/technical-specification.md).
- 에이전트 설계서 v1.1 6-4절(가리기는 LLM 호출 계층과 실행 기록 저장 두 곳), 4-2절 공통 규칙 7(보낸 사람 연락처 열과 고객사 대표 연락처 열은 어떤 호출에도 넣지 않음)(근거: docs/technical/agent-design.md).
- 테이블 정의서 v1.3 §4-2(ticket의 contact_name·contact_email·contact_phone), §2-2(customer의 primary_contact_name·primary_contact_email·primary_contact_phone), §4-4(ticket_message.body 원문, mask_count), §4-10(agent_step.input_json·output_json)(근거: docs/database/table-specification.md).
- 프로젝트 구조 1순위 판 2장(`masking/`, `llm/`, `tests/acceptance/`), 3장 1번 행, 4장(observability/ 제외)(근거: bootcamp/openspec/프로젝트_구조_1순위.md).

용어: **정규식**(regular expression)은 "이런 모양의 글자 묶음"을 찾는 검색 패턴이다. **LLM**은 언어 모델(Gemini)이다.

## Goals / Non-Goals

**Goals**
- 글 하나를 가리는 함수 하나와, LLM 입력이 반드시 지나는 입구 하나를 만든다(근거: 기술 명세서 §7 "함수 `mask_text` 하나를 두 곳에서 부른다").
- 운영진 데이터 4,000건에서 가린 곳 0을 보장한다(근거: 명세서 AC-038-3).

**Non-Goals**
- 메시지 저장, 실행 로그 저장, 화면 표시(proposal "범위 밖").
- DB 구조 변경(근거: 테이블 정의서 v1.3에 필요한 열이 이미 있음).

## Decisions

### 1. 파일 위치와 함수 이름

| 파일 | 내용 | 근거 |
|---|---|---|
| `backend/app/masking/mask.py` | `mask_text(text) -> (masked_text, count)`, `mask_fields(fields) -> (masked_fields, count)`, 예외 `MaskingError` | 함수 이름·반환 꼴은 기술 명세서 §7 "위치". 폴더는 프로젝트 구조 1순위 판 2장 `masking/`. `mask_fields`와 예외 이름은 구현 선택 |
| `backend/app/llm/inputs.py` | `prepare_llm_input(fields) -> LlmInput(fields, mask_count, field_names)`, 금지 항목 목록 `CONTACT_FIELDS` | 위치는 기술 명세서 §7 "(1) LLM 호출 계층"과 프로젝트 구조 1순위 판 3장 1번 행 "llm/ 호출 직전". 함수·자료형 이름은 구현 선택 |
| `backend/tests/acceptance/test_masking.py` | AC-038-1~6 시험 | 프로젝트 구조 1순위 판 2장 "acceptance/ AC 1개 = 시험 1개", CLAUDE.md 규칙 7 |

`mask_text`는 문자열 하나를 받고, `mask_fields`는 사전(dict)·목록(list)을 재귀로 돌며 문자열 값마다 `mask_text`를 부른다(구현 선택. 실행 로그의 input_json·output_json이 JSON 꼴이라 필요하다. 근거: 테이블 정의서 §4-10).

### 2. 검사 순서: 제외 목록을 먼저 보호하고, 그다음 가린다

기술 명세서 §7과 명세서 FR-038 예외 1행은 제외 목록을 먼저 적용하라고 정했다(근거: 기술 명세서 §7 "제외 목록(먼저 적용, 가리지 않음)", 명세서 FR-038 예외 1행). 이를 "보호 → 가리기 → 복원" 세 단계로 구현한다(단계 나누기는 구현 선택).

1. **보호**: 제외 목록에 맞는 글자 묶음을 찾아 임시 표시로 바꿔 둔다(가리기 규칙이 건드리지 못하게).
2. **가리기**: 이메일 → 전화번호 (가) → (나) → (다) 순으로 바꾸고 바꾼 횟수를 센다.
3. **복원**: 임시 표시를 원래 글자로 되돌린다.

제외 목록(1번에서 보호하는 것):

| 제외 대상 | 패턴(설명) | 예 | 근거 |
|---|---|---|---|
| 날짜 꼴 | `YYYY-MM-DD`, `YYYY/MM/DD`. 뒤에 `HH:MM` 또는 `HH:MM:SS`가 붙어도 한 덩어리로 본다 | `2025-10-28` | 기술 명세서 §7 제외 목록. 시각이 붙은 꼴까지 보호하는 것은 구현 선택(가리기 (나)에 걸리지 않게) |
| 영문이 섞인 토큰 | 영문과 숫자가 함께 든 한 단어(`-`, `/` 포함) | `LVB-2024-00117`, `E.OC`, `SWGR-MV-12kV` | 기술 명세서 §7 "영문이 섞인 토큰(제조번호, 에러 코드)" |
| 펌웨어 버전 꼴 | 숫자.숫자(.숫자…) | `2.3.1` | 기술 명세서 §7 "펌웨어 버전 꼴(숫자.숫자)" |
| 금액·수량 | 천 단위 쉼표가 든 수 | `1,250.50` | 기술 명세서 §7 "금액·수량". 꼴은 구현 선택 |
| 이미 가려진 값 | `user…@***.masked`, `COMPANY_…`, `…_AGENT_nn`, `**MASKED**` | `user57705@***.masked` | 기술 명세서 §7, 명세서 FR-038 처리 1 |
| 규격 번호 | 규격 기관 이름(IEC, EN, UL, IEEE, ISO, ANSI, CSA, KS) 바로 뒤의 숫자 묶음 | `IEC 62271-200`, `IEC 62271-100` | **기준 문서의 제외 목록에 없음. 데이터에서 발견**: tickets.csv 4,000건 중 7건(20곳)의 본문·정보 요청·최종 답변에 "IEC 62271-200" 또는 "IEC 62271-100"(숫자 8개 + `-`)이 있어 규칙 (나)에 잘못 걸린다(2026-10-22 직접 셈). AC-038-3(0곳)을 맞추려면 제외해야 한다. 규격 이름 꼴은 ref/product_master.csv standards 열(IEC 60947-2 등)과 같다. **조장 확인 필요**(근거 점검표 2장) |

구분 기호 없는 숫자열은 따로 보호하지 않는다. 규칙 (나)는 구분 기호가 있어야 걸리고, (다)는 0으로 시작하는 10~11자리만 걸리므로 `4500123456`은 어느 규칙에도 맞지 않는다(근거: 기술 명세서 §7 "4로 시작해 (다)가 아님").

### 3. 가리기 규칙(정규식)

| 대상 | 패턴(설명) | 바꾸는 값 | 근거 |
|---|---|---|---|
| 이메일 | 영문·숫자·`._%+-` 1자 이상 + `@` + 도메인 + `.` + 영문 2자 이상. `@***.masked`로 끝나면 제외 | `user***@***.masked` | 기술 명세서 §7 검사식 표 |
| 전화 (가) | `+`로 시작, 숫자·공백·`-`·`.`·괄호 묶음, 숫자 8개 이상 | `*******` | 기술 명세서 §7 (가) |
| 전화 (나) | 숫자 묶음 사이에 구분 기호(공백, `-`, `.`, 괄호)가 하나 이상, 숫자 8개 이상. 앞의 여는 괄호 `(`도 묶음에 넣는다 | `*******` | 기술 명세서 §7 (나). 여는 괄호 처리는 구현 선택 |
| 전화 (다) | 앞뒤에 글자·숫자가 없고, 0으로 시작하는 숫자 10~11자리 | `*******` | 기술 명세서 §7 (다), 명세서 FR-038 처리 2 ② |

가린 곳 수는 바꾼 묶음의 개수다(`+82-10-1234-5678`은 1곳)(근거: 명세서 AC-038-1 "2곳" = 이메일 1 + 전화 1).

### 4. LLM 입력 입구

- `prepare_llm_input(fields)`는 사전 하나를 받는다. 값은 문자열, 숫자, 목록, 사전일 수 있다(근거: 테이블 정의서 §4-10 input_json이 JSON 꼴. 사전으로 받는 것은 구현 선택).
- 항목 이름이 `CONTACT_FIELDS` = {contact_name, contact_email, contact_phone, primary_contact_name, primary_contact_email, primary_contact_phone}에 있으면 `MaskingError(kind="VALIDATION")`로 거부한다(근거: 명세서 FR-038 처리 5·7과 에이전트 설계서 4-2절 공통 규칙 7 "넣지 않는다", 테이블 정의서 §4-2·§2-2 열 이름, 오류 종류 이름은 기술 명세서 §6-5. "거부"로 막는 방식과 VALIDATION을 쓰는 것은 구현 선택).
- 모든 문자열 값을 `mask_fields`로 가린 뒤 `LlmInput(fields=가린 사전, mask_count=합, field_names=항목 이름 목록)`을 돌려준다(근거: 기술 명세서 §7 "(1)", §6-5 "입력 항목 이름 목록"). 항목 이름 목록은 받은 순서다(구현 선택).
- 정규식 실행 중 예상 못 한 오류가 나면 `MaskingError(kind="VALIDATION")`로 바꿔 올린다. 뒤 변경의 LLM 호출 코드는 이 예외가 나면 호출하지 않는다(근거: 기술 명세서 §7 "검사 오류: LLM 호출과 로그 저장을 하지 않고 실행 로그에 오류 종류(VALIDATION)만 남긴다"). 실행 로그에 남기는 일은 FR-036(2순위)이 붙을 때 한다.
- 고객 본문을 `<customer_message>` 안에 넣는 것은 프롬프트를 만드는 쪽(5번 변경)의 일이다. 입구는 가리기만 한다(근거: 기술 명세서 §3-3, CLAUDE.md 규칙 5).

AC-038-3은 DB에 정답지가 들어 있어야 한다. 2번 변경의 시험(test_data_load.py)이 같은 조건(DB + 데이터 폴더)을 쓰므로 README 5번 "시험 실행" 절차를 바꾸지 않는다(근거: README.md 5번, 2번 변경 design 결정 6 "데이터 폴더가 없으면 시험은 실패한다"). AC-038-7은 proposal "범위 밖"대로 이번에 시험하지 않는다.

## Risks / Trade-offs

- [0으로 시작하는 10~11자리 주문 번호가 있으면 잘못 가려진다] → 기준 문서가 이미 받아들인 한계다. 상담원이 체크리스트(FR-013)에서 값을 직접 넣는다(근거: 기술 명세서 §7 "0으로 시작하는 10~11자리 주문 번호가 있으면 잘못 가려질 수 있다", 명세서 FR-038 예외 1행).
- [규격 번호 제외를 넣지 않으면 AC-038-3이 실패한다] → 결정 2의 "규격 번호" 행. 조장 확인 뒤 기술 명세서 §7 제외 목록에 한 줄 추가를 제안한다(근거: 명세서 AC-038-3, tickets.csv 7건 직접 확인).
- [이메일 도메인 꼴이 아닌 주소(예: 점이 없는 도메인)는 가려지지 않는다] → 기술 명세서 §7 검사식이 "`.` + 2자 이상 영문"을 요구하므로 그대로 따른다(근거: 기술 명세서 §7 검사식 표 이메일 행).
