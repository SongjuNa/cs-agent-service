# Proposal: 개인정보 가리기 (add-masking)

## Why

우리 시스템이 새로 받는 글(시뮬레이터 입력, 고객 회신, 상담원이 고친 초안)에는 이메일 주소나 전화번호가 들어 있을 수 있다(근거: 명세서 v1.5 FR-038 기능 설명). 이런 글은 원문 그대로 DB에 저장해 상담원 화면에 보이되, 언어 모델(LLM)에 보내는 입력과 실행 로그에는 이메일·전화번호를 가린 글만 들어가야 한다(근거: 명세서 FR-038 기능 설명, 기술 명세서 v1.4 §7, 1순위 결정 목록 가-7). 다음 변경(5번 `add-inquiry-understanding`)부터 LLM을 부르기 시작하므로, 그 전에 "가리는 함수"와 "LLM 입력이 반드시 지나는 입구"를 먼저 만든다(근거: 프로젝트 구조 1순위 판 6장 4번 `add-masking` = FR-038, 6장 끝 "3·4번은 언어 모델 없이 정답과 바로 비교할 수 있어 먼저 한다").

가리기는 규칙(정규식)으로 하며 LLM을 쓰지 않는다(근거: 명세서 FR-038 처리 2 "가리는 규칙(LLM 아님)", 기술 명세서 §7 "검사식 (규칙 기반이며 LLM 아님)").

## What Changes

- **가리는 함수 `mask_text(text) -> (masked_text, count)`**: 글 하나를 받아 이메일은 `user***@***.masked`로, 전화번호는 `*******`로 바꾸고 바꾼 곳의 수를 함께 돌려준다(근거: 기술 명세서 §7 "위치"·검사식 표, 명세서 FR-038 처리 2·출력).
  - 전화번호 꼴 세 가지: (가) `+`로 시작하고 숫자 8개 이상 (나) 숫자 8개 이상이 구분 기호(공백, `-`, `.`, 괄호)로 이어진 것 (다) 구분 기호 없이 0으로 시작하는 10~11자리 휴대폰 번호(예 `0501234567`)(근거: 기술 명세서 §7 검사식 표, 명세서 FR-038 처리 2 ①②, 팀 정답지 GS-075).
  - 제외 목록을 먼저 적용해 날짜, 주문 번호(`PO 4500123456`), 제조번호(`LVB-2024-00117`), 에러 코드(`E.OC`), 펌웨어 버전, 금액·수량은 가리지 않는다(근거: 기술 명세서 §7 제외 목록, 명세서 FR-038 처리 2·예외 1행).
  - 데이터에 이미 있는 가린 값(`user57705@***.masked`, `COMPANY_2464_0436`, `TS_TRF_AGENT_09`, `**MASKED**`)은 그대로 둔다(근거: 명세서 FR-038 처리 1, 기술 명세서 §7 제외 목록).
- **LLM 입력 입구 `prepare_llm_input(fields)`**: 뒤 변경들의 LLM 호출(L1~L8)이 모두 지나가는 함수 하나를 LLM 호출 계층(`backend/app/llm/`)에 둔다. 입력 항목의 모든 글을 `mask_text`로 가리고, 가린 곳 수와 넣은 항목 이름 목록을 돌려준다(근거: 기술 명세서 §7 "위치 (1) LLM 호출 계층: L1~L8의 모든 입력을 보내기 직전", 명세서 FR-038 의존성 "검사 위치(LLM 호출 계층과 로그 저장 계층에 두어 모든 경로가 거치게)", 기술 명세서 §6-5 "입력 항목 이름 목록"). 보낸 사람 연락처 열(ticket.contact_name·contact_email·contact_phone)이 입력에 들어 있으면 거부한다(근거: 명세서 FR-038 처리 5·7, 기술 명세서 §7 "보낸 사람 연락처 열은 LLM 입력과 실행 로그에 넣지 않는다"). 고객사 대표 연락처(customer의 primary_contact_name·primary_contact_email·primary_contact_phone)도 같이 거부한다(근거: 에이전트 설계서 v1.1 4-2절 공통 규칙 7 "어떤 호출에도 넣지 않는다"). "거부"라는 방식은 구현 선택이다(기준 문서는 "넣지 않는다"까지만 정함).
- **실행 로그용 가리기 `mask_fields(fields)`**: JSON 꼴 값(사전·목록)의 글을 모두 가리는 함수. 실행 로그(agent_step의 input_json·output_json, `LOG_FULL_LLM_IO=true`면 프롬프트·응답 전문)를 저장하는 쪽이 이 함수를 부른다(근거: 기술 명세서 §7 "위치 (2) 실행 로그 저장", §6-5 "요약에 들어가는 글은 모두 가린 글이다", §1-5 환경 변수 `LOG_FULL_LLM_IO`). 실행 로그 저장 자체(FR-036)는 2순위라 이번에는 함수만 두고 저장 코드는 만들지 않는다(근거: 프로젝트 구조 1순위 판 4장 "observability/ FR-036 2순위").
- **검사 오류 처리**: 가리기 중 규칙 오류가 나면 LLM 호출을 하지 않고 오류 종류 `VALIDATION`을 들고 멈춘다(근거: 기술 명세서 §7 "검사 오류", §6-5 오류 종류 목록, 명세서 FR-038 예외 2행).
- **시험**: AC-038-1, 2, 3, 5, 6을 단위 시험으로 만든다(근거: 기술 명세서 §7 "확인" 목록). AC-038-4도 함수 수준에서 더한다(근거: CLAUDE.md 규칙 7 "AC 하나마다 테스트 하나"). §7 확인 목록에 있는 AC-038-7은 아래 "범위 밖"을 본다.

## Capabilities

### New Capabilities
- `masking`: 이메일·전화번호를 규칙으로 가리는 동작과, LLM 입력이 반드시 지나는 입구(근거: 기술 명세서 §7, 프로젝트 구조 1순위 판 2장 `masking/`, `llm/`).

### Modified Capabilities
- 없음.

## 범위 밖

- **원문 저장과 mask_count 기록**: 메시지를 저장할 때 원문을 쓰고 `ticket_message.mask_count`에 가린 곳 수를 넣는 일은 메시지를 처음 저장하는 변경(접수 입력 `POST /tickets`, 발송 FR-031)이 `mask_text`의 count를 받아 한다(근거: 기술 명세서 §7 "메시지를 저장할 때 가린 곳 수(mask_count)만 함께 계산해 둔다", 테이블 정의서 v1.3 §4-4 mask_count, 프로젝트 구조 1순위 판 2장 api/tickets.py). AC-038-1의 "저장된 INQUIRY 본문에는 원문이 그대로"는 그때 확인한다.
- **AC-038-7(연락처 원문 표시)**: 기술 명세서 §7은 이것도 단위 테스트로 만들라고 하지만, 시뮬레이터 접수(FR-001)는 2순위이고 연락처 표시(ticket의 contact_name·contact_email·contact_phone)는 화면 정의서 v2 부록 B(2순위 화면 SCR-03-L L-01)에만 있어 1순위 화면 SCR-03M에는 없다(근거: 화면 정의서 v2 범위 표·부록 B, 프로젝트 구조 1순위 판 4장 "화면 3개" 제외). 그래서 이번 변경에서 확인할 수 없고, 연락처 열이 schema.sql에 있는 것만 전제로 둔다(근거: 테이블 정의서 v1.3 §4-2 ticket.contact_name·contact_email·contact_phone). **조장 확인 필요**(근거 점검표 3장 2번).
- **AC-038-4의 "답변 초안에 고객사 이름"**: 초안 생성(FR-021)은 7번 변경이다. 이번에는 `mask_text`가 `COMPANY_…` 값을 바꾸지 않는 것만 확인한다(근거: 프로젝트 구조 1순위 판 6장 7번 `add-drafts`).
- **실행 로그 저장(agent_step 쓰기)**: FR-036은 2순위이며 1순위는 서버 로그로 대신한다(근거: 프로젝트 구조 1순위 판 4장). `mask_fields`만 두고 저장 코드는 만들지 않는다.
- **운영진 데이터 적재 경로의 검사**: 명세서 FR-038 처리 6은 운영진 데이터 적재(FR-003·035)도 같은 검사를 거친다고 한다. 4,000건을 svc 메시지로 넣는 적재는 시연 데이터 작업 W5이며 1순위에서 뺐다(근거: 프로젝트 구조 1순위 판 4장 "jobs: … 시연 데이터 W5"). 이번에는 gold 표의 글에 함수를 돌려 0곳인지만 확인한다(AC-038-3).
- **상태 객체의 `body_masked`와 검사 오류 시 run FAILED**: 처리 흐름(TicketState, T1)을 만드는 5번 변경에서 입구 함수를 불러 채운다(근거: 기술 명세서 §2-2 T1 행, §2-3 body_masked, 프로젝트 구조 1순위 판 2장 pipeline/state.py).
- **사용자 표시 문구** "개인정보 n곳(LLM·로그에는 가림)", "처리 실패: 마스킹 검사": 화면 몫이라 이번에 만들지 않는다(근거: 명세서 FR-038 출력·예외 2행, FR-035 예외 4행).
- **본문 속 사람 이름 가리기**: 범위 밖(근거: 명세서 FR-038 처리 5, 기술 명세서 §7 "본문 속 사람 이름은 범위 밖").
- **제목(inquiry_subject)을 LLM 입력에서 빼는 검사**: 문의 이해(L1) 입력을 만드는 5번 변경에서 다룬다(근거: 기술 명세서 §3-3 "제목·정답 열은 넣지 않는다", §2-3).
- **가린 값 복원 기능**: 두지 않는다(근거: 명세서 FR-038 예외 3행).

## Impact

- 새 파일: `backend/app/masking/mask.py`(가리는 함수), `backend/app/llm/inputs.py`(LLM 입력 입구), `backend/tests/acceptance/test_masking.py`(시험)(근거: 프로젝트 구조 1순위 판 2장 masking/, llm/, tests/acceptance/).
- 고치는 파일: 없음. DB 구조(`docs/database/schema.sql`)와 `.env.example`은 그대로다(근거: 테이블 정의서 v1.3 §4-2·§4-4·§2-2에 연락처 열과 mask_count가 이미 있음).
- 새 라이브러리: 없음. 파이썬 표준 `re`(정규식)만 쓴다(구현 선택).
