# Proposal: 검증 에이전트 (add-verification-agent)

## Why

코드 검사(Q11)는 인용과 숫자만 본다. 그래서 근거에 없는 "30% 할인"처럼 숫자는 근거 절(견적 유효기간 30일)과 같지만 뜻이 틀린 문장은 통과한다(근거: 기술 명세서 v1.4 §3-4 5번, 명세서 v1.5 AC-049-1). 이런 뜻의 문제를 언어 모델이 한 번 더 읽어 찾고, 상담원에게 표시만 한다(근거: 명세서 FR-049 기능 설명, 가-10). 이번 변경이 그 검증 단계를 만든다(근거: 프로젝트 구조 1순위 판 6장 8번 `add-verification-agent` = FR-049).

## What Changes

- **검증 단계(Q14, L8)를 그래프 끝에 더한다**: 초안 → 코드 검사(Q11) → 대역(L7) → **검증(L8)** → 끝(승인 대기). 코드 검사는 그대로 둔다(근거: FR-049 처리 1, 기술 명세서 §2-1 하위 문의 그래프, 에이전트 설계서 v1.1 3-5절).
  - 정보 요청 초안과 답변 초안 모두 초안마다 1회 검증한다(근거: 기술 명세서 §3-1 L8 행 "DRAFT 초안마다 1회(정보 요청·답변)").
- **확인 항목 4가지**: 근거와 뜻이 다른 문장(MEANING_MISMATCH), 약속 표현(PROMISE), 질문과 다른 답(OFF_TOPIC), 한국어 대역 오역(GLOSS_MISTRANSLATION)(근거: FR-049 처리 2, 기술 명세서 §3-2 L8 검증 출력).
- **입력**: 이 하위 문의의 고객 요청 문장, 초안 본문, 대역, 근거 절 본문, 조회값. 모두 가린 글이다(근거: FR-049 입력, 에이전트 설계서 4-10절 입력, 기술 명세서 §2-2 Q14 행). 부서 회신은 이관(FR-033)이 3순위라 늘 비어 있다(근거: 명세서 v1.5 기능 목록 "FR-033 MVP 3순위", config.yaml 1순위 목록).
- **결과**: 지적마다 {kind, quote, reason}의 목록(기술 명세서 §3-2)과, 그 목록에서 만든 4항목별 "문제 있음 / 문제 없음 / 확인 못 함"(FR-049 처리 3·출력)을 함께 낸다. 코드가 quote가 초안이나 대역에 실제로 있는지 보고, 없으면 그 지적만 버린다. 지적이 없으면 ⑤ 통과다(근거: 기술 명세서 §3-2 L8, 에이전트 설계서 4-10절 코드 검사).
- **대역이 없을 때**: 대역 오역 항목만 빼고 3항목을 검증하고 gloss_checked = false로 둔다(근거: FR-049 예외 3행, 에이전트 설계서 4-10절 "대역이 없을 때").
- **실패할 때**: 30초, 1회 재시도. 그래도 실패하면 초안은 그대로 두고 통과로 보이지 않게 한다(근거: FR-049 처리 6·7, 예외 2행). 오류 종류(LLM_TIMEOUT, LLM_INVALID_OUTPUT)는 검증 결과의 detail에 남긴다(근거: 에이전트 설계서 4-10절 저장 `{"error": ...}`).
- **검토 표시 ⑤ 상태와 문구**: 검증 결과에서 상태(PASSED / FOUND / FAILED)와 문구("⑤ 통과", "⑤ 걸림: {항목}", "⑤ 검증 못 함(실패)", 대역 없음 꼬리말)를 만드는 함수를 둔다(근거: 기술 명세서 §5-7 review_marks no 5 state, 에이전트 설계서 6-3절 ⑤ 행). 화면에 붙이는 일은 9번 변경이다(근거: FR-024 처리 6, 에이전트 설계서 4-10절 화면, 4-10절 "화면 이름은 차례로 뜻 다름 / 약속 표현 / 질문과 다름 / 대역 오역").
- **지시문**: `prompts/l8_verify_v1.md`(에이전트 설계서 4-10절 초안)(근거: 에이전트 설계서 4-2절 3번).

## Capabilities

### New Capabilities
- `verification`: 초안마다 언어 모델로 뜻의 문제 4가지를 찾고, 지어낸 지적을 코드로 버리고, ⑤ 문구를 만드는 동작.

### Modified Capabilities
- 없음. `drafts`의 초안 객체에 검증 결과 칸을 더하지만 drafts 요구사항은 바뀌지 않는다(구현 선택).

## 범위 밖

- **검증 결과 저장(eval.self_check, check_type = VERIFY)**: VERIFY 행은 저장된 초안(message_id)이 있어야 하는데 초안 저장이 아직 없다(근거: schema.sql self_check_draft_message 제약, 개발_결정_기록 C-30). 이번에는 초안 객체에 결과를 붙여 돌려준다. 칸 이름은 self_check 열(passed_yn, detail, checked_at_utc)과 detail 모양({findings, gloss_checked} 또는 {error})을 따른다(근거: 테이블 정의서 v1.3, 에이전트 설계서 4-10절 저장).
- **실행 로그(agent_step)의 검증 실패 기록**: 실행 로그 화면·기록(FR-036)은 2순위다(근거: 명세서 v1.5 기능 목록 "FR-036 MVP 2순위", 프로젝트 구조 1순위 판 4장).
- **AC-049-2(검사 5개 통과), AC-049-3(⑤가 걸린 초안 승인 확인 창), AC-049-4의 화면·승인 버튼 부분**: 검토 표시 화면(FR-024)과 승인(FR-031)은 9번 변경이다(근거: 프로젝트 구조 1순위 판 6장 9번). 9번 변경에 넘길 목록은 개발_결정_기록 변경 8 절에 둔다(구현 선택). ⑤ 검증 실패 초안은 지적이 없으므로 "그래도 발송" 확인을 받지 않는 것(에이전트 설계서 7-1 L8 실패 행)도 함께 넘긴다. 이번에는 AC-049-4의 "두 번 시간 초과 → 초안 유지, ⑤ 검증 못 함, 오류 LLM_TIMEOUT"까지 시험한다.
- **[다시 검증] API(`POST /messages/{draft_id}/verify`)와 "고친 뒤 검증 안 함"(STALE)**: 저장된 초안(draft_id)과 임시 저장(FR-031)이 있어야 한다(근거: 기술 명세서 §8-1, §5-7). FR-049 기능이지만 저장이 생기는 9번 변경에서 만든다(구현 선택. 개발_결정_기록 C 항목).
- **리마인드(FR-023)와 예외 부서 메일(FR-033 처리 9)을 검증하지 않는 것**: 두 기능이 1순위 밖이라 해당하는 초안이 없다(근거: FR-049 처리 8, config.yaml 1순위 목록).
- **문제 문장 강조**: 화면 일이라 9번 변경이다. 이번에는 강조할 quote를 결과에 남긴다(근거: FR-049 처리 4, 프로젝트 구조 1순위 판 6장 9번).
- **채점(사람이 표시한 정답과 재현율·정밀도)**: 표시 건수가 미정이다(근거: 에이전트 설계서 4-10절 채점 "미정").

## Impact

- 새 파일: `prompts/l8_verify_v1.md`, `backend/app/llm/verify.py`, 시험 파일(근거: 프로젝트 구조 1순위 판 3장 13행 "llm/, checks/"). ⑤ 상태·문구 함수는 검증 결과 객체에 붙여 `llm/verify.py`에 둔다. 구조 2장은 검토 표시를 checks/에 두므로, ①~⑤를 함께 계산하는 일은 9번 변경에서 checks/에 둔다(구현 선택).
- 고치는 파일: `backend/app/pipeline/graph.py`(verify 노드), `backend/app/llm/drafts.py`(초안 객체에 verify 칸)(구현 선택).
- DB 구조는 고치지 않는다(구현 선택).
