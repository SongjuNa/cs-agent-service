# Design: 복합 문의 분리와 답변 구성

## Context

동기는 proposal.md의 Why를 본다. 따를 기준은 다음과 같다(근거: 아래 문서들).
- 명세서 v1.5 FR-006(처리 1~5, 예외 3행, AC-006-1~3), FR-022(처리 1~8, 예외 4행, AC-022-1~4), FR-036 AC-036-4, D15·D16·D18.
- 기술 명세서 v1.4 §2-1 두 겹 그래프, §2-2 T3·T5 행, §2-3 상태 객체(multi_yn), §2-4, §2-5 분기① ③ 복합 답변 구성, §3-4 누락 검사, §6-2.
- 에이전트 설계서 v1.1 4-6(L4 모드: 단일 = 완성문, 복합 = 단락), 4-7(L5, 메일 조립), 6-1(숫자 허용 = 상태 목록의 문의 번호, 누락 검사 = 상태 목록 줄 수), 부록 A-2(S-1~S-6), A-3(F-2).
- schema.sql: ticket.multi_yn, sub_ticket(sub_ticket_id, seq), agent_run.sub_ticket_id(티켓 그래프는 비움), ticket_message.sub_ticket_id.

## Goals / Non-Goals

**Goals**
- 요청 n개를 하위 문의 n개로 나눠 각각 처리하고, 답변 초안이 생긴 하위 문의마다 상태 목록이 붙은 메일 초안을 만든다(근거: FR-006 처리 3·4, FR-022 처리 1·3).

**Non-Goals**
- 팀 정답지 채점, 같은 부서 묶기, 동시 실행, 14개 언어 문안, 화면(proposal "범위 밖") (근거: proposal 범위 밖).

## Decisions

### 1. 나누기 (`app/llm/understand.py`, `app/pipeline/understand.py`)

| 정한 것 | 내용 | 근거 |
|---|---|---|
| 요청 목록 | L1 결과의 sub_tickets를 같은 유형끼리 합친 뒤(1순위 merge_same_category) 순번 순 목록으로 돌려준다. 합친 뒤 seq를 1..n으로 다시 매긴다 | FR-006 처리 2·3, 예외 1행 "근거 문장을 모두 남김". 다시 매기기는 구현 선택 |
| 긴급도 | 하위 문의마다 자기 요청의 긴급도. 같은 유형을 합칠 때만 높은 쪽 | FR-006 처리 4 "자기 문의의 유형과 근거 문장으로 FR-007", 1순위 merge_same_category |
| 확신 낮음 | 하위 문의마다 자기 확신도로 표시 | FR-005 처리(1순위 그대로, 하위 문의 단위로) |
| 추출(L2) | 하위 문의마다 자기 근거 문장과 그 유형의 필수 항목으로 부른다 | §2-1 Q1, FR-006 처리 4 |
| 복합 표시 | "복합 문의 가능(FR-006, 2순위)" 표시를 없애고 TicketState.multi_yn = (n ≥ 2) | §2-3 multi_yn, FR-006 처리 3 |

### 2. 하위 문의별 처리 (`app/pipeline/graph.py`)

- 노드 순서: understand → rules → info_request(막는 정보가 있는 하위 문의만) → evidence → reply(막는 정보가 없는 하위 문의만) → compose(T5) → gloss → verify. 단일 문의는 n = 1인 같은 흐름이다(근거: §2-1 "단일 문의는 n = 1인 경우일 뿐 같은 그래프", §2-5 분기③ ④. 한 그래프 안에서 노드가 하위 문의마다 고르는 것은 구현 선택).
- 노드는 하위 문의를 순번 순으로 처리한다. 한 하위 문의에서 오류가 나면 그 하위 문의의 pipeline_error에 "자동 처리 실패. 다시 시도"를 남기고 나머지는 계속한다(근거: FR-006 예외 3행, §2-2 T3 "실패한 하위 문의만 표시(pipeline_error), 나머지 계속". 순차 처리는 C-90).
- 복합 문의의 답변 초안은 L4 단락 모드("Write ONE paragraph for this request only; greeting and closing are added separately.")로 부른다(근거: 에이전트 설계서 4-6 모드).
- 사용량을 하위 문의에 나눌 수 있게 노드가 하위 문의를 처리하는 동안 RunLog가 지금 하위 문의를 안다(`RunLog.sub(sub_ticket_id)`)(근거: FR-036 처리 2, C-89. 방법은 구현 선택).

### 3. 답변 메일 구성 T5 (`app/pipeline/compose.py`, `app/llm/wrap.py`)

| 정한 것 | 내용 | 근거 |
|---|---|---|
| 언제 | 복합 문의(multi_yn)에서 FINAL_REPLY 초안이 생긴 하위 문의마다 한 통. 정보 요청 초안은 감싸지 않는다 | FR-022 처리 1·2, §2-5 복합 답변 구성 |
| 조립 | 인사말 → 단락 → 빈 줄 → "Status of your requests:" → 상태 줄(seq 순) → 맺음말 | 에이전트 설계서 4-7 메일 조립, 부록 A-2, FR-022 처리 3·4 |
| 인사말·맺음말 | L5(`l5_wrap_v1.md`, 에이전트 설계서 4-7 지시문 초안 그대로, 결과 {"greeting","closing"}). 실패하면 F-2 고정 문구 | 4-7, 부록 A-3 F-2, FR-022 출력 |
| 상태 줄 | 이 메일의 하위 문의 = S-1. 그 밖: RESOLVED·CLOSED = S-2, WAITING_CUSTOMER = S-4, ESCALATED = S-5, 처리 실패·근거 없음(초안 없음) = S-6, NEW·IN_PROGRESS = S-3 | 부록 A-2 표, FR-022 처리 3·7, 예외 3행 |
| 줄을 만드는 대상 | 이 티켓의 하위 문의 행 전부(svc.sub_ticket). 고객 회신 재처리처럼 일부 하위 문의만 다시 처리할 때도 나머지 줄을 DB 상태로 넣는다 | FR-022 처리 3 "이 티켓의 하위 문의 n개 각각", 예외 1행 |
| 상태를 읽는 때 | 메일을 만드는 때의 상태(sub_ticket.status)와 이번 실행 결과(실패·초안 없음). 이미 만든 초안은 나중에 고치지 않는다 | FR-022 처리 3 "현재 상태", 예외 4행 |
| 주제 이름 | {topic} = 1순위 L4가 쓰는 유형 영어 이름(CATEGORY_NAMES)의 첫 글자를 대문자로(예 Quotation, Firmware update) | 부록 A-2 "{topic}은 유형의 고객용 이름(예 Quotation, Firmware update)". 10종 목록은 1순위 구현 선택 |
| 언어 | 상태 줄은 영어 원문만 있다. 다른 언어 메일에도 영어 줄을 붙인다 | 부록 A-2, 에이전트 설계서 T40, FR-022 처리 3 (C-92) |
| 템플릿 위치 | `app/templates/status_list/en.json`(머리, S-1~S-6) | 구현 선택(리마인드 템플릿과 같은 폴더 방식) |
| 자체 대조 | 조립한 메일 전체를 그 하위 문의의 근거·조회값·제공 항목 + 상태 목록의 문의 번호(1..n)로 대조한다. 결과가 그 메일의 DRAFT_CHECK가 된다 | FR-022 처리 5, 에이전트 설계서 6-1 2번, §3-4 |
| 누락 검사 | 상태 줄 수 < 하위 문의 수면 1회 다시 조립, 그래도 모자라면 "상태 목록 누락" 표시 | FR-022 예외 1행, 에이전트 설계서 6-1 3번 |
| 기한 없음 | 상태 문구는 부록 A-2 문장만 쓴다(시간·날짜 없음) | FR-022 처리 3, AC-022-4 |

- 상담원이 고친 메일의 다시 대조(임시 저장·발송)에도 같은 문의 번호를 허용한다(근거: FR-031 처리 2 "같은 검사", 에이전트 설계서 6-1 2번).

### 4. 저장 (`app/db/store.py`)

- n ≥ 2이면 ticket.multi_yn = true, 없는 sub_ticket 행(seq 2..n)을 넣고 접수 시각으로 NEW 이력을 남긴다(근거: FR-006 처리 3, §2-4 실행 시작 "이해 전에는 seq 1 하나", FR-025 전이 INTAKE. 넣는 때는 구현 선택).
- 실행 기록: 하위 문의가 둘 이상인 결과는 티켓 run(이번 실행)에 T2(하위 문의별 몫 목록)·T5·T6을, 하위 문의마다 새 run(같은 trigger, sub_ticket_id = 그 문의)에 Q 단계와 자체 검사를 쓴다. 하나뿐이면 지금처럼 한 run(근거: AC-036-4, AC-036-1, 테이블 정의서 v1.3 agent_run.ticket_id).
- 접수 실행은 sub_ticket_id 없이 연다(티켓 그래프 실행)(근거: 테이블 정의서 v1.3 agent_run.ticket_id "티켓 그래프 실행은 sub_ticket_id가 없어서 둔다", 기술 명세서 §6-2 agent_run 행. 이 변경 전에는 `{ticket_id}-1`로 열었다).

### 5. 하위 문의의 실행 찾기 (`app/db/runs.py`, `reprocess.py`, `detail.py`)

- 하위 문의 S의 실행 = 같은 티켓의 처리 흐름 실행 중 sub_ticket_id = S이거나 비어 있는 것의 가장 최근 것(근거: FR-036 처리 5 "같은 ticket_id·순번의 run이 여러 개면 가장 최근 것". 규칙은 구현 선택).
- T2 결과가 하위 문의별 몫 목록이면 그 문의의 seq 몫을 쓴다(상세 "왜?", 회신 재처리의 query_en)(근거: §2-1 T2는 티켓 그래프, 구현 선택).
- 상세 응답 ticket에 category_code(';')와 multi_yn을 더한다(근거: FR-006 출력·사용자 표시).

### 6. 시험 (`tests/acceptance/test_compound_inquiry.py`)

- AC-006-1: CSV1-000008(대역 L1이 FW_UPDATE·MANUAL 두 요청) → 하위 문의 2개, category_code "FW_UPDATE;MANUAL", multi_yn true, 하위 문의 run 2개(근거: AC-006-1).
- AC-006-2: CSV1-000004 → "QUOTE", multi_yn false, run 1개(근거: AC-006-2).
- AC-006-3: 복합 티켓의 하위 문의 run마다 Q3·Q4·Q6 출력이 그 문의의 유형으로 계산한 값과 같다(근거: AC-006-3).
- AC-036-4: 하위 문의 run 2개와 T5가 든 티켓 run(sub_ticket_id 없음)(근거: AC-036-4).
- AC-022-1: FW_UPDATE 하위 문의의 메일에 펌웨어 단락(RN 인용)과 "2. Manual and document: …" 줄이 있다(근거: AC-022-1).
- AC-022-2: 그 메일을 발송하면 FW_UPDATE 하위 문의만 RESOLVED(근거: AC-022-2).
- AC-022-3: MANUAL 하위 문의의 근거가 없으면 FW_UPDATE 메일의 상태 목록에 S-6 줄, MANUAL 하위 문의에 "근거 없음"(근거: AC-022-3).
- AC-022-4: 상태 목록에 시간·날짜가 없다(근거: AC-022-4).
- 그 밖: 회신 재처리 메일의 상태 목록도 하위 문의 2개, 메일 구성(T5) 실패 → 단락만 있는 초안을 남기지 않음·"근거 없음" 표시 없음, L5 실패 → F-2, 하위 문의 하나 실패 → 나머지 계속·S-6, 상태 목록 누락 검사, 정보 요청 하위 문의 + 답변 하위 문의(근거: FR-022 예외 1·3행, FR-006 예외 3행, FR-022 처리 2).

## Risks / Trade-offs

- C-90: 하위 문의를 차례로 처리해 티켓 처리 시간이 하위 문의 수만큼 늘어난다(근거: §2-4 시간 상한).
- C-92: 아랍어 등 다른 언어 메일에 영어 상태 목록이 붙는다. CSV1-000008은 ar이다. FR-022 처리 3·§2-5는 "고객 언어로"를 요구하므로 팀의 T40 번역·검수 전까지의 임시 처리다(근거: tickets.csv language, T40, 리마인드 문안 C-74와 같은 처리). 팀 확인 필요.
- C-91: FR-022/FR-006 예외 2행은 "그 하위 문의만 다시 묻기"인데 §3-2는 응답 전체를 스키마로 검사해 1회 다시 부른다. 문서끼리 다르므로 1순위 방식(전체 1회 다시)을 두고 팀 확인을 받는다(근거: FR-006 예외 2행, §3-2).
- C-95: 고객 회신이 하위 문의 하나만 대상으로 하면 그 실행은 하위 문의 run으로 열려(1순위 회신 재처리 그대로) T5가 그 run에 남는다. AC-036-4는 접수 실행만 본다(근거: AC-036-4, FR-032).
- C-96: 다시 처리(RETRY)에서 요청 수가 줄면 이전 하위 문의 행과 multi_yn이 그대로 남는다. 행을 지우지 않는 저장 규칙(§6-2 INSERT만) 때문이며 화면 쪽 정리는 변경 19에서 본다(근거: 기술 명세서 §6-2).
