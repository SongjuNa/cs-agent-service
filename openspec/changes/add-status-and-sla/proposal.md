# Proposal: 상태 관리와 SLA 두 시계 (add-status-and-sla)

## Why

2순위의 리마인드(FR-023), 경고(FR-027), 고객 회신(FR-032), 접수함(FR-029), 티켓 상세(FR-030)는 문의 상태나 SLA 두 시계를 읽는다(근거: 명세서 v1.5 FR-025 "9. 의존성" 후행 "FR-023, FR-026, FR-027, FR-031~033", FR-026 후행 "FR-027, FR-029, FR-030"). 1순위에서는 접수 이력(INTAKE)만 남기고 상태를 바꾸지 않았다(근거: 개발_결정_기록 C-37). 이번 변경에서 정해진 전이표대로만 상태를 바꾸고, 두 시계를 이력에서 계산해 보여 준다(근거: 명세서 FR-025 처리 1~5, FR-026 처리 1~6, 기술 명세서 v1.4 §6-4).

## What Changes

- **상태 전이 (`app/status/`)**: 상태는 DB 함수 `svc.transition()` 하나로만 바꾼다. 허용 전이표에 없는 전이는 "현재 상태(○○)에서는 할 수 없는 작업"으로 거부한다(근거: 기술 명세서 §6-4 "상태를 바꾸는 함수는 하나", 명세서 FR-025 처리 1, 예외 1행, schema.sql svc.transition).
  - 처리 흐름이 끝나면 NEW인 하위 문의를 IN_PROGRESS(PIPELINE_DONE)로 바꾼다(근거: 기술 명세서 §2-2 T6 행, 명세서 FR-001 처리 4). 처리 흐름이 실패하면 NEW로 둔다(근거: §2-2 T2 행 "티켓 NEW 유지, run FAILED", FR-001 예외 표). 전이 자체가 실패하면 NEW로 두고 실행을 PARTIAL로 끝낸다(근거: §2-2 T6 실패 칸 "전이 실패 → NEW 유지, run PARTIAL").
  - 승인·발송이 상태를 바꾼다: 정보 요청 → WAITING_CUSTOMER(INFO_REQUEST_SENT), 최종 답변 → RESOLVED(FINAL_REPLY_SENT)(근거: 명세서 FR-031 처리 4, FR-025 전이표). 전이표에 없는 전이면 발송 기록은 남기고 상태는 그대로 두며 실행 로그를 남긴다(근거: FR-031 예외 3행 "발송 기록은 남기되 상태는 바꾸지 않음, 실행 로그 기록").
  - 같은 문의를 두 사람이 동시에 바꾸면 먼저 저장된 것만 반영하고, 뒤 요청에는 "다른 사용자가 먼저 변경함. 새로고침"을 돌려준다(근거: 명세서 FR-025 예외 2행, schema.sql sub_ticket.version).
- **자동 종료 점검 (`app/status/closing.py`)**: 기준 시각(as_of)을 받아 무응답 168시간 종료(WAITING_CUSTOMER → CLOSED, final_action = CLOSED_NO_RESPONSE)와 해결 뒤 168시간 종료(RESOLVED → CLOSED)를 한다. 기준은 마지막 INFO_REQUEST(또는 FINAL_REPLY) SENT 시각 + 168시간이고 그 뒤 고객 회신이 없을 것이며, 전이 시각은 점검 시각이 아니라 그 시각이다(근거: 기술 명세서 §6-4 주기 점검 3·4, "시계 돌리기", 명세서 FR-025 처리 4·4-1, D20, D22). 5분마다 부르는 스케줄러는 11번 변경(FR-027)에서 붙인다(근거: 명세서 FR-025 처리 4 "FR-027의 주기 점검과 함께 돈다").
- **SLA 두 시계 (`app/sla/`)**: DB 함수 `svc.inquiry_sla(as_of)`로 1차 응답·해결 경과와 상태, 남은 시간, 대기 시간 합을 읽는다. 값은 저장하지 않는다(근거: 명세서 FR-026 기능 설명, 기술 명세서 §6-4 "SLA는 저장하지 않고", schema.sql inquiry_sla). 목표가 비면 "SLA 미정", 경과가 음수면 0과 "시간 기록 확인 필요"로 보인다(근거: FR-026 예외 1·3행).
- **상세 API (`GET /tickets/{id}`)**: 하위 문의마다 상태, SLA 두 시계, 상태 이력, 대기 구간 목록, 해결 시각을 더하고(상세 API에 넣는 것은 구현 선택. 기술 명세서 §8-1의 `GET /tickets/{id}/timeline`은 아래 범위 밖), 티켓 머리에 대표 상태를 더한다(근거: 명세서 FR-025 출력, 처리 5, FR-026 출력, 기술 명세서 §6-4 티켓 대표값, schema.sql svc.v_ticket_summary).
- **채점용 정답지 재생 (`jobs/replay_gold.py`)**: 운영진 데이터의 시각(접수, 1차 응답, 대기 시간, 해결)을 scoring 스키마에 상태 이력으로 재생하고, 목표는 정답 우선순위로 다시 조회해, `scoring.inquiry_sla(스냅샷)`을 정답과 비교한 결과를 eval_run·eval_case·eval_summary와 csv로 남긴다(근거: 기술 명세서 §10-1 3번 "목표 시간은 정답 우선순위로 조회한다", 4번 출력. 근거: 기술 명세서 §10-1 3번 "SLA·상태 항목은 정답지의 시각으로 재생", 1번 "SLA 계산식: 운영진 데이터 4,000건 전체", CLAUDE.md 규칙 6 "시험·채점 코드만 예외").

## Capabilities

### New Capabilities
- `status-sla`: 상태 전이와 이력, 자동 종료 점검, SLA 두 시계 계산과 상세 표시, 정답지 재생 채점.

### Modified Capabilities
- `ticket-detail`: "상태는 NEW 그대로", "상태 전이는 하지 않는다"는 1순위 요구 문장을 MODIFIED 델타로 고친다. 처리 끝 상태 전이와 발송 뒤 상태 전이를 더한다(1순위 범위 밖이던 AC-031-1·2의 상태 부분, 근거: 개발_결정_기록 C-37).

## 범위 밖

- **고객 회신 입력(FR-032)과 AC-025-2, FR-025 예외 3·4행**: 13번 변경에서 만든다(근거: 명세서 FR-025 입력 "고객 회신 입력(FR-032)", 2순위 변경 순서 13번. 변경 순서는 bootcamp/openspec/2순위_시작_전후비교.md 결정 2, 조장 승인 2026-10-23).
- **5분 스케줄러와 SLA 경고(FR-027)**: 11번 변경(근거: 기술 명세서 §6-4 주기 점검 1, 2순위 변경 순서 11번).
- **이관 전이(ESCALATE, DEPT_REPLY, DEPT_MAIL_SENT)**: FR-033이 3순위다(근거: 명세서 기능 목록 "FR-033 MVP 3순위"). 재생 채점에서만 이관 상태를 이력으로 만든다(아래 design 결정 6).
- **팀 정답지(W9) 적재와 AC-025-5·026-6의 팀 정답지 채점**: 팀 정답지가 아직 DB에 없다(근거: 개발_결정_기록 C-3은 1순위에서 W9를 뺀 결정이고, 2순위 적재는 정하지 않았다 → C-55). SLA 계산식은 기술 명세서 §10-1 1·3번대로 운영진 4,000건으로 채점하고, 상태 재생은 §10-3 "생성·존재 기록"대로 이력이 생긴 건수만 기록한다.
- **화면의 상태 배지·두 시계·이력 탭**: 티켓 상세 전체판(FR-030)에서 그린다(근거: 화면 정의서 v2 0-1절 "상태 배지, SLA 두 시계와 경고"는 최소판이 하지 않음, 2순위 변경 순서 19번). 이번에는 API에만 넣는다.
- **회신 요청 리마인드 126시간(FR-023, FR-025 처리 4)**: 14번 변경(근거: 2순위 변경 순서 14번).
- **`GET /tickets/{id}/timeline`(기술 명세서 §8-1)**: 메시지·상태 이력·경고·조정을 합친 목록이라 경고(11번)·조정(12번)·회신(13번) 뒤 티켓 상세 전체판(19번)에서 만든다. 이번에는 상세 API에 상태 이력만 넣는다(구현 선택).
- **목표가 바뀌면 상태만 다시 판정(FR-026 처리 6)**: 우선순위 조정(FR-028) 12번 변경. inquiry_sla가 현재 목표를 읽으므로 계산 쪽은 고칠 것이 없다. (근거: 명세서 FR-026 처리 6, 2순위 변경 순서 12번)
- **접수함의 대표 상태(FR-025 출력, FR-029)**: 18번 변경(뷰 svc.v_inquiry_inbox·v_ticket_summary는 이미 있다). (근거: 명세서 FR-025 출력, 2순위 변경 순서 18번)
- **진행 안내(FR-048)**: 여유 시 기능이다(근거: 명세서 FR-048 "여유 시 2순위, MVP 밖").

## Impact

- 새 파일: `backend/app/status/transitions.py`, `backend/app/status/closing.py`, `backend/app/sla/clock.py`, `jobs/replay_gold.py`, 시험 파일(구현 선택. 기술 명세서 §6-4는 함수 이름만 정함).
- 고치는 파일: `backend/app/db/store.py`(처리 끝 전이, 발송 뒤 전이), `backend/app/db/detail.py`(상태·SLA·이력), `backend/app/api/messages.py`(동시 수정 오류, 전이 거부 안내), 1순위 시험 `test_ticket_detail.py`(AC-015-4의 상태 값, AC-031-1·2의 상태 부분). (근거: 이 변경의 design 결정 2·5)
- DB 구조는 고치지 않는다(근거: CLAUDE.md 규칙 4). 전이표·함수·뷰는 schema.sql에 이미 있다.
