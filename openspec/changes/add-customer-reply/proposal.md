# Proposal: 고객 회신 입력과 메시지 이력 (add-customer-reply)

## Why

시나리오 ⓑ(필수정보 누락 → 요청 → 대기 → 회신 → 해결)의 가운데 단계가 없어서, 정보 요청을 보낸 문의가 대기에서 벗어나지 못한다(근거: 명세서 v1.5 FR-032 기능 설명). 상담원이 고객 회신을 대신 입력하면 대기가 끝나고, 회신에서 제공 항목을 다시 뽑아 새 초안을 만들어야 한다(근거: FR-032 기능 설명, 기술 명세서 v1.4 §2-4 "고객 회신 재처리"). 메시지 이력은 1순위에서 표와 저장 규칙이 생겼고, 이 변경에서 고객 회신 행과 조회를 더한다(근거: FR-035 처리 1·2·7, schema.sql svc.ticket_message).

## What Changes

- **회신 저장 (`app/db/replies.py`)**: 회신 본문을 CUSTOMER_REPLY RECEIVED(보낸 쪽 고객) 한 행으로 원문 저장하고 가린 곳 수를 남긴다(근거: FR-032 처리 1, FR-035 처리 1·2·5).
  - 대상 문의가 WAITING_CUSTOMER면 IN_PROGRESS로 바꿔 대기 구간을 닫고, RESOLVED면 IN_PROGRESS로 바꿔 자동 종료를 멈춘다. 그 밖의 상태는 그대로 두고 저장만 한다(근거: FR-032 처리 2, FR-025 예외 3행, schema.sql status_transition CUSTOMER_REPLY 2행).
  - 거부: 빈 본문("회신 내용을 입력하세요"), 요청 발송보다 앞선 시각("회신 시각은 요청 발송 이후여야 합니다"), 미래 시각(근거: FR-032 입력·예외 1·2행, 화면 정의서 v1 SCR-03-P6).
  - 종료(CLOSED) 문의는 메시지만 저장하고 다시 처리하지 않는다("종료 후 회신으로 기록됨")(근거: FR-032 예외 3행).
- **다시 처리 (`app/pipeline/reprocess.py`)**: 회신으로 IN_PROGRESS가 된 문의를 Q1(원문 + 모든 회신)부터 다시 돌린다. 저장만 하는 상태에서는 돌리지 않는다(근거: FR-032 처리 2·3, FR-025 예외 3행. 두 문장이 다르게 읽혀 C-72). 제공 항목은 합집합으로 늘기만 한다. 막는 항목이 남으면 새 정보 요청 초안, 없으면 근거·답변 초안을 만든다(근거: FR-032 처리 3·4, 기술 명세서 §2-4 "고객 회신 재처리", §2-5 분기⑥).
  - 실행 계기는 CUSTOMER_REPLY, 이전 초안은 superseded_at으로 밀어낸다(근거: 기술 명세서 §2-4 "재처리", §6-5 trigger).
  - 상담원이 조정한 우선순위와 SLA 목표는 덮어쓰지 않는다(근거: FR-011 예외 3행, 개발_결정_기록 C-69).
- **API**: `POST /tickets/{id}/replies`(body, language, received_at, target_sub_ticket_ids)(근거: 기술 명세서 §8-1, 화면 정의서 v1 SCR-03-P6).
- **상세 API**: 메시지 이력(SENT·RECEIVED 행 시각순, 순번 필터), 정보 요청 초안의 "재요청" 표시, 재문의 횟수(근거: FR-035 처리 7·출력, FR-032 처리 4·6, 화면 정의서 v1 SCR-03-P6 결과).
- **AC-025-2**: 10번 변경이 이 변경으로 넘긴 완료 기준(회신으로 대기 구간 1개가 닫힘)을 함께 확인한다(근거: 개발_결정_기록 변경 10 범위 밖, FR-025 AC-025-2).

## Capabilities

### New Capabilities
- `customer-reply`: 고객 회신 저장, 상태 전이, 회신 뒤 다시 처리, 메시지 이력 조회.

## 범위 밖

- **"회신 수신 확인" 진행 안내 초안(FR-032 처리 5, AC-032-4 뒷부분)**: 명세서 v1.4부터 전이별 안내는 FR-048(여유 시, MVP 밖)이고 FR-023에는 리마인드만 남았다. FR-032 처리 5의 "FR-023이"와 달라 C-71로 묻는다(근거: FR-023 머리말, FR-048 처리 1 ③, AC-048-2).
- **아래 띠와 회신 입력 화면(SCR-03-P6, B-01)**: 19번 변경(근거: 같은 순서표 19번).
- **AC-035-1·2(운영진 데이터 메시지 적재)**: 운영진 데이터 적재(FR-003) 17번 변경(근거: FR-035 처리 6, 같은 순서표 17번).
- **AC-035-5(복합 문의 순번)**: 복합 문의 16번 변경. 그중 PROGRESS_NOTICE 행은 리마인드(14번)만 MVP에 있다(근거: 같은 순서표 16번, FR-048 Could Have).
- **AC-035-6(리마인드 자동 발송 행)**: 리마인드 14번 변경(근거: 같은 순서표 14번).
- **회신 화면의 "개인정보 n곳" 표시와 문의 순번 필터의 화면**: API는 notes와 seq 인자로 돌려주고, 화면은 19번(근거: FR-035 예외 4행·처리 7, 같은 순서표 19번).
- **회신 글자 위치(span)**: 접수 때와 같이 비워 둔다. 화면 강조를 만들 때 정한다(근거: FR-030 처리 1, 같은 순서표 19번).
- **허용되지 않은 종류·상태 조합의 실행 로그(FR-035 예외 1행)**: DB CHECK가 저장을 거부하지만 실행 로그는 15번 실행 로그 변경에서 본다(근거: 같은 순서표 15번).

## Impact

- 새 파일: `backend/app/db/replies.py`, `backend/app/pipeline/reprocess.py`, 시험 파일(근거: 이 변경의 design 결정 1~3).
- 고치는 파일: `backend/app/pipeline/graph.py`(이해 단계 바꿔 끼우기), `backend/app/db/store.py`(회신 결과 저장), `backend/app/api/tickets.py`(회신 API), `backend/app/db/detail.py`(메시지 이력·재요청·재문의) (근거: design 결정 2~4).
- DB 구조는 고치지 않는다. ticket_message, inquiry_field, status_transition은 schema.sql에 이미 있다(근거: CLAUDE.md 규칙 4).
