# ticket-detail Specification

## Purpose
접수한 문의와 처리 결과를 저장하고, 상담원이 티켓 상세 최소판(화면 정의서 v2 SCR-03M)에서 근거와 검토 표시 5개를 보고 초안을 고쳐 승인·발송한다(명세서 v1.5 FR-024, FR-031, FR-039, FR-049).

## Requirements

### Requirement: 접수와 처리 결과를 저장한다 (FR-038)
접수 API는 미등록 고객을 거부하고, 티켓·하위 문의·INQUIRY 메시지(원문, 가린 곳 수)·접수 이력을 한 트랜잭션으로 저장한 뒤 처리 흐름을 백그라운드로 돌려야 한다(MUST)(근거: 기술 명세서 v1.4 §2-4, §8-1 POST /tickets, 명세서 FR-038 처리 3). 처리가 끝나면 판단값, 초안(DRAFT), 대역, 자체 검사, 실행 기록을 저장해야 하며, 실행 기록에는 가린 글만 넣어야 한다(MUST)(근거: §6-2, §7). 초안은 DRAFT로만 저장해야 하고, 초안을 만든다고 상태가 바뀌어서는 안 된다(MUST)(근거: CLAUDE.md 규칙 3, 명세서 AC-015-4). 처리 흐름이 끝나면 NEW → IN_PROGRESS로 바꾼다(근거: 기술 명세서 §2-2 T6, 명세서 FR-001 처리 4, 개발_결정_기록 C-51). 이 저장은 FR-031 화면의 선행 작업이다.

#### Scenario: AC-015-4 초안은 DRAFT로만 있고 상태는 그대로다
- **GIVEN** CSV1-000017을 접수해 정보 요청 초안이 만들어진 상태
- **WHEN** 발송 전 메시지 이력과 상태를 본다
- **THEN** 초안은 DRAFT 행으로만 있고 하위 문의 상태는 처리 흐름 종료로 바뀐 IN_PROGRESS다(이력 INTAKE, PIPELINE_DONE)

#### Scenario: AC-038-1 원문은 저장되고 실행 기록은 가려진다
- **GIVEN** 본문 "contact me at kim@example.com or +82-10-1234-5678"로 접수
- **WHEN** 저장된 INQUIRY 행과 실행 기록을 본다
- **THEN** INQUIRY 본문은 원문 그대로이고 mask_count는 2이며, 실행 기록에는 "kim@example.com"과 "1234-5678"이 없다

### Requirement: 근거 영역과 검토 표시 5개를 보인다 (FR-024)
상세 API는 저장된 값만 읽어 단계 순서대로 "결과 — 근거" 줄과 확인 표시 모음을 돌려주고, 근거가 비면 그 줄만 "없음(사유)"로 보여야 한다(MUST)(근거: 명세서 FR-024 처리 1·2·4·5, 예외 1행). 초안마다 검토 표시 5개를 읽을 때 계산하고, ④는 "걸림"이 아니라 "확인 필요: 안전 문의"로 보여야 한다(MUST)(근거: FR-024 처리 6, 기술 명세서 §5-7). 인용을 누르면 절 본문을 돌려주고, 본문이 없으면 "본문 열기 실패"를 돌려줘야 한다(MUST)(근거: FR-024 처리 3, 예외 2행, 화면 정의서 P2).

#### Scenario: AC-024-1 CSV1-000017의 근거 줄
- **GIVEN** 처리가 끝난 CSV1-000017
- **WHEN** 티켓 상세를 연다
- **THEN** 긴급도 근거 문장, PR-02 판정 과정, RT-LV_BREAKER-DEFECT와 이관 조건, serial_no 막는 항목, SLA-DEFECT-PLATINUM-P1이 보이고, 정보 요청 분기라 근거 절 줄은 "없음(정보 요청 중)"이다(고장 진단·이관 후보 줄은 3순위라 없음)

#### Scenario: AC-024-2 인용을 누르면 절 본문이 열린다
- **GIVEN** CSV1-000064(정답지 reference DS-CONT-MC-32a §2.1) 답변 초안의 "(DS-CONT-MC-32a §2.1)" 인용
- **WHEN** 그 절을 연다
- **THEN** DS-CONT-MC-32a §2.1의 절 본문이 돌아오고, 없는 절이면 "본문 열기 실패"다

#### Scenario: AC-024-3 분류 실패 줄
- **GIVEN** 분류가 실패한 티켓
- **WHEN** 상세를 연다
- **THEN** 유형 줄은 "없음(분류 실패)"이고 나머지 줄은 정상이다

#### Scenario: AC-024-4 안전 문의
- **GIVEN** 긴급도 SAFETY인 CSV1-000202의 초안
- **WHEN** 검토 표시를 본다
- **THEN** ④가 "④ 확인 필요: 안전 문의"이고 표시는 5개다

### Requirement: 초안을 임시 저장하고 승인·발송한다 (FR-031)
임시 저장은 DRAFT 본문만 바꾸고 대역을 다시 만들며 검증은 다시 부르지 않아야 한다(MUST)(근거: 명세서 FR-031 처리 7, FR-039 AC-039-4, 추가 결정 가3). 승인·발송은 상담원 ID와 본문을 확인해야 한다(MUST)(근거: 화면 정의서 v2 0-3, P7 오류 문구). 최종 본문의 자체 대조 불일치(답변은 인용·숫자, 정보 요청은 막는 항목 라벨)·검증 지적·남은 막는 항목이 있으면 확인을 받은 뒤에만 보내고 그 선택을 기록해야 한다(MUST)(근거: FR-031 처리 2, 예외 5행, FR-049 처리 5, 에이전트 설계서 6-1). 발송은 SENT 행을 새로 쓰고 초안을 APPROVED로 바꾸며 처음 발송이면 1차 응답 시각을 기록해야 한다(MUST)(근거: FR-031 처리 3·5). 같은 초안은 한 번만 보내야 한다(MUST)(근거: FR-031 예외 4행). 발송 뒤 상태 전이는 status-sla 요구를 따른다(근거: FR-031 처리 4, config.yaml "FR-031의 발송 뒤 상태 전이는 FR-025·026 변경에서 붙인다").

#### Scenario: AC-031-1 정보 요청 발송
- **GIVEN** CSV1-000017의 정보 요청 초안
- **WHEN** 승인·발송한다
- **THEN** INFO_REQUEST SENT 행이 생기고 1차 응답 시각이 발송 시각으로 기록되며 상태가 WAITING_CUSTOMER가 된다

#### Scenario: AC-031-2 고친 답변 발송
- **GIVEN** CSV1-000004 답변 초안에서 한 문장을 고친 경우
- **WHEN** 승인·발송한다
- **THEN** SENT 행의 수정 여부가 Y이고 원본 초안 행은 글자가 바뀌지 않은 채 APPROVED이며 상태가 RESOLVED가 된다

#### Scenario: AC-031-3 근거 밖 숫자
- **GIVEN** 답변 초안에 조회값에 없는 숫자를 써 넣은 경우
- **WHEN** 승인을 누른다
- **THEN** "근거 밖 숫자" 확인이 요구되고, 그래도 발송하면 발송되며 override_check가 기록된다

#### Scenario: AC-031-5 두 번 승인
- **GIVEN** 이미 발송한 초안
- **WHEN** 두 번째 승인 요청이 온다
- **THEN** 거부되고 SENT 행은 1건이다

#### Scenario: AC-039-2 발송 본문에 대역이 없다
- **GIVEN** CSV1-000004 프랑스어 답변 초안을 승인·발송한 뒤
- **WHEN** SENT 행을 본다
- **THEN** 본문은 프랑스어 초안뿐이고 대역 문장이 없다

#### Scenario: AC-039-4 임시 저장하면 새 대역
- **GIVEN** 상담원이 초안 한 문장을 고쳐 임시 저장한 경우
- **WHEN** 대역을 본다
- **THEN** 고친 문장이 반영된 새 대역이다

### Requirement: 검증 결과를 ⑤로 보이고 다시 검증한다 (FR-049)
⑤는 그 초안의 최신 검증 결과로 통과·걸림·검증 못 함·고친 뒤 검증 안 함을 보여야 하며, [다시 검증]은 검증을 1회 더 부르고 새 행으로 남겨야 한다(MUST)(근거: 명세서 FR-049 처리 4·7, 기술 명세서 §5-7, §8-1 verify). ⑤가 걸린 초안은 확인을 받아 보내고, 검증 못 함인 초안은 확인 없이 보낼 수 있어야 한다(MUST)(근거: FR-049 처리 5, 에이전트 설계서 7-1).

#### Scenario: AC-049-2 검사 5개 통과
- **GIVEN** 코드 검사와 검증을 모두 통과한 초안(나머지 표시도 통과)
- **WHEN** 검토 표시를 본다
- **THEN** "검사 5개 통과"다

#### Scenario: AC-049-3 ⑤가 걸린 초안 승인
- **GIVEN** ⑤가 걸린 초안
- **WHEN** 상담원이 승인한다
- **THEN** 확인이 요구되고, 그래도 발송하면 발송되며 그 선택이 기록된다

#### Scenario: AC-049-4 검증 실패 초안
- **GIVEN** 검증 호출이 두 번 모두 시간 초과
- **WHEN** 티켓 상세를 연다
- **THEN** 초안과 ①~④가 보이고 ⑤는 "검증 못 함(실패)"이고 [다시 검증]을 할 수 있으며, 확인 없이 승인할 수 있고 실행 기록에 LLM_TIMEOUT이 남는다

### Requirement: 티켓 상세 묶음 (FR-030)
상세는 원문·제목·연락처·추출 값, 하위 문의마다 유형·긴급도·우선순위(규칙값과 최종값)·부서·SLA·필수 항목과 근거, 하위 문의별 초안을 보여야 한다(MUST)(근거: FR-030 처리 1~3, 기술 명세서 §8-1 GET /tickets/{id}).

#### Scenario: AC-030-1 정보 요청 문의
- **GIVEN** CSV1-000017을 접수한 뒤
- **WHEN** 상세를 연다
- **THEN** 원문과 강조할 error_code, DEFECT·SITE_DOWN·P1(PR-02)·TS_LV·SLA 1h/24h·막는 항목 serial_no, 정보 요청 탭에 영어 초안이 보인다

#### Scenario: AC-030-2 우선순위 근거
- **GIVEN** 같은 상세의 우선순위 P1
- **WHEN** "왜?"를 누른다
- **THEN** PR-02 규칙 행과 긴급도 SITE_DOWN의 근거 문장이 보인다

#### Scenario: AC-030-3 복합 문의
- **GIVEN** CSV1-000008(복합)을 접수한 뒤
- **WHEN** 상세를 연다
- **THEN** 문의 1(FW_UPDATE)과 문의 2(MANUAL) 구역이 따로 있고 각자 근거 문장이 있으며 답변 탭에 하위 문의별 초안이 있다

#### Scenario: AC-030-4 막는 항목 없는 견적
- **GIVEN** CSV1-000004(QUOTE)를 접수한 뒤
- **WHEN** 상세를 연다
- **THEN** 정보 요청 탭은 "막는 항목 없음"이고 답변 탭에 프랑스어 초안과 조회값 520 USD·4주가 보인다

#### Scenario: 없는 번호
- **GIVEN** 없는 ticket_id
- **WHEN** 상세를 연다
- **THEN** 404 "티켓을 찾을 수 없음"이고 화면은 접수함으로 돌아간다

### Requirement: 분류 직접 수정 (FR-030 처리 6)
상담원이 유형·긴급도·제품·반품 구분·받은 항목을 고치면 "상담원 수정"으로 표시하고 그 하위 문의를 규칙 단계부터 다시 돌려야 한다(MUST)(근거: FR-030 처리 6, AC-030-5, AC-010-3, AC-013-3, 기술 명세서 §2-4 부분 재실행).

#### Scenario: AC-030-5 유형 수정
- **GIVEN** 처리가 끝난 하위 문의
- **WHEN** 상담원이 유형을 바꿔 저장한다
- **THEN** "상담원 수정" 표시가 붙고 우선순위·부서·필수 항목·SLA 목표가 새 유형으로 다시 계산된다

#### Scenario: AC-013-3 받은 항목
- **GIVEN** 막는 항목 serial_no가 빠진 하위 문의
- **WHEN** 상담원이 serial_no를 받았다고 저장한다
- **THEN** missing_blocking_info에서 serial_no가 빠지고 정보 요청 필요가 꺼진다

#### Scenario: 충돌
- **GIVEN** 다른 상담원이 먼저 바꾼 하위 문의
- **WHEN** 이전 version으로 저장한다
- **THEN** 409 "다른 사용자가 변경함. 새로고침"

### Requirement: 다시 처리 (FR-030 처리 5)
처리 중이 아닌 티켓은 언제든 새 실행으로 다시 처리할 수 있어야 하며, 이전 초안은 대체됨으로 표시하고 발송한 메시지는 지우지 않아야 한다(MUST)(근거: FR-030 처리 5, 기술 명세서 §2-4 재처리 행).

#### Scenario: 성공한 티켓 다시 처리
- **GIVEN** 초안이 있는 티켓
- **WHEN** [다시 처리]를 누른다
- **THEN** 새 RETRY 실행이 생기고 이전 초안은 superseded, 새 초안이 보인다

### Requirement: 이력 (FR-030 처리 4)
이력은 메시지·상태 변경·경고·우선순위 조정을 시각순 한 줄 목록으로 보여야 한다(MUST)(근거: FR-030 처리 4, 기술 명세서 §8-1 timeline 행).

#### Scenario: 시각순 이력
- **GIVEN** 접수·정보 요청 발송·우선순위 조정이 있는 티켓
- **WHEN** 이력을 연다
- **THEN** 상태 변경, 발송 메시지, 조정 줄이 시각 오름차순으로 보인다
